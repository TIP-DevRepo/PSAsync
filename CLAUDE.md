# Verification before calling a task done
Run `npm run lint` and `npm run build` before considering a change complete. Fix errors these surface rather than leaving them for the user to find. A change that adds or edits an API route also runs `npm run check:routes`, which must pass.

# Package manager
This repo uses npm exclusively (`package-lock.json` is the source of truth). Never introduce a `yarn.lock` or `pnpm-lock.yaml`, and don't suggest yarn/pnpm commands.

# Dependency versions
Key dependencies are newer than typical training data: Next.js 16.2.9, React 19.2.4, Prisma 7.8. Before using an API from these, check `node_modules/next/dist/docs/` (per AGENTS.md), `node_modules/prisma`, or the installed type defs rather than assuming familiar behavior. APIs have moved between major versions.

# Scope discipline
Keep changes scoped to what was asked. Don't refactor, rename, or "clean up" unrelated code while fixing a bug or adding a feature. Separate cleanup into its own explicitly-requested change.

# Secrets and config
`.env*` files are gitignored. Never read or write any `.env*` file (`.env`, `.env.local`, `.env.development.local`, etc.) by any means: no `Read`, `cat`, `Get-Content`, `grep`/`Select-String` over them, no `Write`/`Edit`, no shell redirection into them. Never commit them, print their contents, or hardcode values from them into source. If a task needs a new env var, tell the user in your summary which variable to add, to which file, and why. Do not add it yourself.

# Branching and commits (project conventions)
- I create and switch branches myself and name them `feature/*` or `bugfix/*`. Claude Code works on whichever branch is currently checked out and never creates or switches branches. If the checked out branch looks wrong for the task (for example `main` or `dev`), stop and ask me before making any changes.
- Branch naming: `feature/short-description` for new features, `bugfix/short-description` for bug fixes.
- Commit titles are plain, short, and present-tense, with no code block formatting. Example: "Add dashboard grid layout scaffold".
- Never invent, guess, or assume a version number (vX.X.XX). Use one only when my prompt gives it to you, and then the commit title starts with it, for example "v0.9.04: Short Title". Otherwise commit titles have no version number.
- Never use em dashes or en dashes anywhere: not in code comments, not in commit messages, not in any generated text. Use a comma, colon, or period instead.

# Environment variables: critical gotcha
- The running app (`src/auth.ts`, `src/lib/prisma.ts`) and `prisma/seed.ts` all build their database connection from five separate environment variables: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`. They do NOT read `DATABASE_URL`.
- Prisma CLI commands (`migrate dev`, `migrate deploy`, `migrate reset`) read `DATABASE_URL` from `prisma.config.ts` instead.
- This means a script or command that appears to target one database via `DATABASE_URL` may silently run against a completely different database if `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` are set differently in the active environment.
- Before running any command that writes, seeds, or migrates data, explicitly check and state which actual database the current `DB_HOST`/`DB_NAME` values point to. Never assume `DATABASE_URL` and `DB_NAME` are in sync.
- Never run `prisma/seed.ts` or any destructive script without first confirming the active `DB_NAME` is not the live production database, unless explicitly instructed to target production.

# Prisma conventions
- Run `npx prisma format` before every migration.
- When adding a relation between two models that already share another relation, explicitly name it with `@relation("Name")` on both sides, or `prisma format` will error on ambiguous relations.
- Always include the migration name inline in migrate commands, e.g. `npx prisma migrate dev --name add_dashboard_and_widget_models`, never leave it to prompt interactively.

# Project structure
- Prisma schema at `prisma/schema.prisma`.
- API routes under `src/app/api/`, following Next.js App Router conventions (`route.ts` with GET/POST/PATCH/DELETE exports, params as a Promise in dynamic segments).
- Shared components in `src/components/`, organized by feature area (`src/components/inventory/`, `src/components/clients/`, etc).

# API routes
- Every new or changed route handler starts with `const { ctx, response } = await requireAccess(rule?)` from `src/lib/api-access.ts` and returns `response` if set. Use `ctx.companyId` and `ctx.userId`, never the session token's values.
- Ids from the URL go through a scoped loader in `src/lib/scoped-loaders.ts`, never a bare id lookup. A miss returns `notFound()`. Updates and deletes use the matching `*Where` builder so the write itself is company scoped.
- Ids that arrive in a request body (tag ids, location ids, vendor ids, etc.) must be validated against the caller's company before use.
- Use `assertRefs(ctx, { ... })` from `src/lib/scoped-loaders.ts` for body ids: it checks them all in one query per record type, skips empty values, and returns a ready 400 (or null when valid). Add a new key there rather than writing a one off lookup.
- Responses use explicit `select` objects. Errors use the shape `{ error, code? }`.
- Every route declares the permission it needs in the `requireAccess` call itself, for example `requireAccess({ permission: "quotes.edit", message: "You do not have permission to edit quotes" })`, never as a separate check further down. A missing permission is a 403 with code `FORBIDDEN` and a short plain `message`. A record the user may not open is a 404 `{ error: "Not found" }`, the same as one that doesn't exist.
- Reads shared by several pages (pickers, search) use an any-of rule, `permission: ["pages.quotes", "pages.catalog", ...]`, where holding one is enough.
- Every quote route runs the quote view check (VQ) on its URL id: `loadViewableQuote`, or `viewableQuoteWhere` when the route needs its own include, both in `src/lib/scoped-loaders.ts`. A user may open a quote with `pages.quotes` and then only their own, everyone's with `quotes.viewAllUsersQuotes`, or one waiting on an approval they can decide. Lists, totals, and widgets filter with `quoteListWhere`. Writes after the check use `quoteWhere`.
- Every sales order route runs the sales order view check (VSO) on its URL id, and every purchase order route the purchase order view check (VPO): `loadViewableSalesOrder` / `viewableSalesOrderWhere` and `loadViewablePurchaseOrder` / `viewablePurchaseOrderWhere` in `src/lib/scoped-loaders.ts`. The line item and attachment loaders there run the same check on their parent order. A user may open an order with the page permission (`pages.salesOrders` / `pages.purchaseOrders`) and then only their own (the order's `userId`, which for an order created when a quote is accepted is the quote's owner) unless they hold `salesOrders.viewAll` / `purchaseOrders.viewAll`. A miss is a 404. Lists and widgets filter with `salesOrderListWhere` / `purchaseOrderListWhere`; writes after the check use `salesOrderWhere` / `purchaseOrderWhere`.
- Sales order keys: list and detail need `pages.salesOrders`, create `salesOrders.create`, status `salesOrders.changeStatus`, every other field (notes included), line items, and attachment uploads and deletes `salesOrders.edit`, delete `salesOrders.delete`; comments only need VSO. Purchase orders follow the same pattern with the `purchaseOrders.*` keys, and receiving needs `purchaseOrders.edit`. Generating a purchase order from sales order lines needs `salesOrders.generatePO` and VSO on that sales order; a manual purchase order needs `purchaseOrders.create`. `GET /api/so-po-settings` needs `settingsSections.salesOrders` (only its settings panel reads it).
- Settings reads: `company-settings`, `microsoft-settings` (never returns the client secret, only `hasClientSecret`), `quote-settings`, `distributors/enabled`, and `distributor-search/preferences` are open to any active user. `notification-settings` needs `settingsSections.notifications` and `approval-workflows` (GET) needs `settingsSections.approvalWorkflows`. `GET /api/users` and `GET /api/roles` are open to any active user for pickers, but email addresses and each role's `permissions` are only returned with `settingsSections.users`.
- `GET /api/dashboards/widget-data` gives each widget the same visibility as its page. A widget the user may not see answers `200 { type, noAccess: true }` with no data, and the tile shows a no access note.
- Line item cost, and margins worked out from it, is only returned when `canSeeCost(ctx)` (`src/lib/api-access.ts`) is true; otherwise leave it out with `omitCost`, and the UI shows "-" (`canSeeCostWith` in `src/lib/access-check.ts` holds the shared rule). Anything that copies cost into another record reads it from the database, never from the request.
- The same rule covers the catalog and distributor search. `GET /api/catalog` (the picker list) leaves `cost` out of every item unless `canSeeCost(ctx)`, so every consumer types it as `cost?: number` and shows "-" when it is missing. `GET /api/distributor-search` leaves out each offer's `price` and `cost` (both are the company's dealer pricing) on the same condition. `GET /api/catalog/[id]` needs `pages.catalog`, which already implies seeing cost.
- Line item cost is never trusted from the browser. Quote, quote template, sales order, and purchase order line item POSTs set cost with `newLineItemCost` (`src/lib/line-item-cost.ts`): a caller with `canSeeCost` gets the cost they sent when it is a finite number, otherwise the catalog item's stored cost (company scoped), and 0 with no catalog item; a caller without `canSeeCost` always gets the catalog item's cost, or 0. PATCHes only write cost when `mayWriteCost` allows it, so a caller without `canSeeCost` never changes a stored cost. Purchase order lines call the field `unitCost`; omit it with `omitUnitCost`. Sales order and purchase order detail responses leave cost out unless `canSeeCost`, and their pages show "-". `PATCH /api/catalog/[id]` only writes the fields the request includes. List totals worked out from cost (purchase order and vendor purchase order lists) are left as they are.
- Open picker routes, any active user with no rule beyond `requireAccess()`: `GET` on `clients`, `clients/[id]`, `contacts/search`, `catalog` (cost aside), `categories`, `industries`, `contact-tags`, `inventory-custom-fields`, and `vendors`. Forms on other pages (quotes, orders, inventory) read them, so never put a page permission on these.
- Clients: creating and importing needs `clients.create`; editing a client, its contacts, and its locations needs `clients.edit`. Client assets, inventory onboarding, and a site's default container need `pages.inventory`. There is no client DELETE route.
- Catalog, vendors, and inventory routes need their page permission (`pages.catalog`, `pages.vendors`, `pages.inventory`). Catalog DELETE needs `catalog.delete`; inventory asset and stock DELETE need `inventory.delete`; asset Remove needs `pages.inventory` and `inventory.delete`. Catalog order history and a vendor's purchase orders only list the user's own sales or purchase orders (`userId`) unless they hold `salesOrders.viewAll` or `purchaseOrders.viewAll`, the same rule as the order lists.
- Company settings lists: writes to categories, custom fields, and contact tags, and deleting an industry, need `settingsSections.company`. Their settings panels gate on it with `useAccess` and show `SettingsNoAccess`, since the lists themselves load for anyone.
- Any-of rules in this area: `POST /api/industries` takes `settingsSections.company`, `clients.create`, or `clients.edit` (the client forms add an industry inline). `GET /api/inventory-locations` and `GET /api/inventory-locations/own-company` take `pages.inventory` or `purchaseOrders.edit` (purchase order receiving reads them).
- Every route handler under `src/app/api` starts with `const { ctx, response } = await requireAccess(...)` unless its route is on the public list at the top of `scripts/check-route-access.ts` (NextAuth, the client portal, and the SSO start, lookup, and callback routes). `npm run check:routes` scans every `route.ts` without a database or network and exits 1 if a handler fails this; new routes must pass it. Only routes the forced password change screen needs pass `allowPasswordGate` (`account/password` today).
- The SSO callback (`src/app/api/sso/callback/route.ts`) compares the `tid` claim of the id token from Microsoft's token endpoint with the company's saved tenant, ignoring case, before linking anything (`checkSsoTenant` in `src/lib/sso-tenant.ts`), and refuses a mismatch with `?error=wrong_tenant`. A tenant saved as a domain name instead of a GUID can't be compared and is skipped. Signing in never changes the owner (`connectedByUserId`) of a mailbox another user connected.
- The Settings page lists only the panels the user may use (`PANEL_PERMISSION` in `src/app/dashboard/settings/page.tsx`), shows `NoAccess` without `pages.settings` or any usable panel, and `SettingsNoAccess` for a `?panel=` link to a hidden one. The Microsoft panel is open to anyone who can open Settings, for their own mailbox; the app credentials, SSO, and other users' mailboxes need `settingsSections.integrations`.
- Client components get the signed in user's access from `useAccess()` (`src/components/AccessProvider.tsx`, filled by the dashboard layout) and use it only to hide or disable UI. Pages the user can't open show `NoAccess` (`src/components/NoAccess.tsx`).
- A new permission key is registered in every one of these places, or saving a role that has it fails: `DEFAULT_PERMISSIONS` in `src/app/api/roles/route.ts`, the Everyone defaults in `src/lib/everyone-role.ts`, `BOOLEAN_SECTIONS` in `src/lib/role-permission-rules.ts`, the `RolePermissions` type in `src/lib/permissions.ts`, `buildGlobalAdminPermissions` in `src/lib/global-admin-role.ts`, and the matching labels list in `src/components/settings/RolesPermissionsPanel.tsx`. A removed key goes in `LEGACY_KEYS` in `role-permission-rules.ts` so older roles still save.

# Dev-only test tooling
- `scripts/dev-only/create-test-companies.ts` creates or tops up two throwaway companies (Test Company B and C) with a Global Admin each and sample data for every company scoped route. Each run prints new admin passwords once, never saved anywhere.
- `scripts/dev-only/check-cross-company.ts` signs in as both admins against the local dev server, runs positive controls, then tries to read and change the other company's records and prints a PASS/FAIL table.
- Both refuse to run unless `DB_NAME` is exactly `psasync_dev`, `NODE_ENV` is not production, and `--yes` is passed (see `scripts/dev-only/lib/guard.ts`). They load only `.env.development.local`, never `.env`.
- Run from the repo root: `npx tsx scripts/dev-only/create-test-companies.ts --yes`, then start `npm run dev` and run `npx tsx scripts/dev-only/check-cross-company.ts --yes` with `TEST_ADMIN_B_PASSWORD` and `TEST_ADMIN_C_PASSWORD` set in the shell.
- Nobody, including Claude Code, runs these against the live database. Claude Code only lints, typechecks, and builds them, and never runs them.
- New attempts go in the `ATTEMPTS` list at the top of the check script.
- `create-test-companies.ts` also gives each test company the permission test users: "Test Everyone B/C" (only the Everyone role, reset to no permissions) and "Test Rep B/C" (only a "Rep" role with `pages.quotes`, `quotes.create`, and `quotes.edit`) with a quote of their own, and "Test Clerk B/C" (only a "Clerk" role with `pages.clients`, `clients.create`, `clients.edit`, `pages.vendors`, `pages.catalog`, and `pages.inventory`) with a sales order and purchase order of their own, plus a placeholder mailbox row for each admin. It also adds a container, a pooled stock item, and a stock row so every inventory route has a record to aim at. "Test Orders B/C" (only an "Orders" role with `pages.salesOrders`, `pages.purchaseOrders`, `salesOrders.create`, `salesOrders.edit`, `purchaseOrders.create`, and `purchaseOrders.edit`; no viewAll, no generatePO) gets a draft sales order and purchase order of their own, each with a line, and "Test Templater B/C" (only a "Templater" role with `settingsSections.quotes`) uses a "Sample Cost Template" with one line. The sample catalog item's cost is reset to `SAMPLE_ITEM_COST` (60) on every run. Their passwords are printed once per run like the admins'.
- All three dev scripts refuse to run if a test company has any Microsoft credentials or an enabled distributor integration (`findExternalServices` in `scripts/dev-only/lib/guard.ts`), so they can never send real email or reach a real distributor. No attempt tests a distributor connection.
- `scripts/dev-only/check-permissions.ts` signs in as Test Admin B, Test Rep B, Test Clerk B, Test Orders B, Test Templater B, and Test Everyone B (plus Test Sender B and Test Viewer B users it sets up itself; the Viewer holds both order pages and both viewAll keys but no edit, so it sees orders without cost), runs positive controls, then checks every quote, sender, mailbox, client, catalog, vendor, company settings list, inventory, sales order, purchase order, settings, users, and roles route allows or refuses each user as expected and changes nothing when refused. Guarded routes in the clients, catalog, vendors, and inventory area are listed once in its `GUARDED` list (refused for Everyone and Rep, and for the Clerk where marked), the order routes in `ORDER_GUARDED` (refused for Everyone, Rep, and Clerk), the settings, users, and roles routes in `SETTINGS_GUARDED` (refused for Everyone), and the open pickers in `PICKERS`; all feed `ATTEMPTS`. It also checks the line item cost rule (a Templater's bogus cost is replaced by the catalog cost) and that a catalog PATCH without cost keeps it. It never sends email: send-email attempts are only ones refused before any mail goes out. Same guard, login, `--base-url`, table, and exit codes (0 pass, 1 FAIL or UNEXPECTED, 2 broken harness) as the cross company check. New attempts go in its `ATTEMPTS` list.
- Run it after `create-test-companies.ts`, with `npm run dev` running and `TEST_ADMIN_B_PASSWORD`, `TEST_REP_B_PASSWORD`, `TEST_EVERYONE_B_PASSWORD`, `TEST_CLERK_B_PASSWORD`, `TEST_ORDERS_B_PASSWORD`, and `TEST_TEMPLATER_B_PASSWORD` set in the shell: `npx tsx scripts/dev-only/check-permissions.ts --yes`.

# Design system conventions
- Use the tinted pill pattern for accent colored badges and status labels: `bg-brand-secondary-500/10 text-brand-secondary-500` style. Avoid hardcoding solid colors with manual dark mode overrides.
- Use existing `brand-primary`/`brand-secondary` CSS variable tokens for theming, never hardcoded hex colors, so everything respects each company's brand colors and both light and dark mode.
- `PSAsync-Design-Rules.md` is the authoritative reference for motion timing, visual hierarchy, tabs, modals, data tables, and forms. Follow it for anything not explicitly stated elsewhere. # Windows environment note
- The `postinstall` script uses touch-style file creation for `.env`, which can behave unexpectedly on Windows. If a fresh `npm install` fails around `.env` creation, this is likely why, not a real project error.

# Deployment note
- After any merge into `main` that includes new Prisma migration files, `npx prisma migrate deploy` must be run against the live production database. This is a manual step performed by the project owner, not something to run automatically as part of a build or deploy script.

## Commits

- Claude Code makes commits itself, locally only. Never create or switch branches, never push, never open pull requests, never merge, never amend or rewrite history, and never force anything. I handle all of that manually.
- Make several small commits instead of one big one. Commit when a logical piece of work or a phase is finished and the build and lint pass for it. Never commit broken or half finished work.
- Stage only the files that belong to each commit. Check git status before each commit and never stage .env files, .next, secrets, or stray files. A schema change and the migration folder it needs go in the same commit.
- Title: short, imperative, plain. Do not include a version number unless my prompt gives one. If it does, the title starts with it, for example "v0.9.04: Short Title".
- Titles match the existing repo history, for example "Fix category picker not updating on add catalog item form".
- Description: plain text, one to four sentences, saying what changed and why in user terms. Never put the description in a code block.
- Never use em dashes or en dashes in commit titles or descriptions.
- Never mention Claude, Claude Code, AI, Anthropic, or any assistant in a commit. No Co-Authored-By, no "Generated with", no trailers of any kind.
- At the end of every task, list the commits you made (short hash and title) in your report.
