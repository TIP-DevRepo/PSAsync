# Verification before calling a task done
Run `npm run lint` and `npm run build` before considering a change complete. Fix errors these surface rather than leaving them for the user to find. A change that adds or edits an API route also runs `npm run check:routes`, which must pass. An upgrade of `next`, `next-auth`, `@auth/core`, or `@auth/prisma-adapter` also runs `npm run check:auth`, which must pass (see Sessions).

# Package manager
This repo uses npm exclusively (`package-lock.json` is the source of truth). Never introduce a `yarn.lock` or `pnpm-lock.yaml`, and don't suggest yarn/pnpm commands.

# Dependency versions
Key dependencies are newer than typical training data: Next.js 16.3.8, next-auth 5.0.0-beta.32 (with @auth/core 0.41.3), React 19.2.4, Prisma 7.8. Before using an API from these, check `node_modules/next/dist/docs/` (per AGENTS.md), `node_modules/next-auth`, `node_modules/prisma`, or the installed type defs rather than assuming familiar behavior. APIs have moved between major versions, and next-auth 5 is still a beta whose behavior can change between beta releases.
- Every upgrade of `next`, `next-auth`, `@auth/core`, or `@auth/prisma-adapter` must keep `npm run check:auth` passing. If it fails, read the installed `node_modules/next-auth/lib/index.js` before changing `src/auth.ts` or the check. `@auth/prisma-adapter` pins an exact `@auth/core`, so it moves together with next-auth to keep a single copy installed.

# Scope discipline
Keep changes scoped to what was asked. Don't refactor, rename, or "clean up" unrelated code while fixing a bug or adding a feature. Separate cleanup into its own explicitly-requested change.

# Secrets and config
`.env*` files are gitignored. Never read or write any `.env*` file (`.env`, `.env.local`, `.env.development.local`, etc.) by any means: no `Read`, `cat`, `Get-Content`, `grep`/`Select-String` over them, no `Write`/`Edit`, no shell redirection into them. Never commit them, print their contents, or hardcode values from them into source. If a task needs a new env var, tell the user in your summary which variable to add, to which file, and why. Do not add it yourself.

# Branching and commits (project conventions)
- I create and switch branches myself and name them `feature/*` or `bugfix/*`. Claude Code works on whichever branch is currently checked out and never creates or switches branches. If the checked out branch looks wrong for the task (for example `main` or `dev`), stop and ask me before making any changes.
- Branch naming: `feature/short-description` for new features, `bugfix/short-description` for bug fixes.
- Commit titles are plain, short, and present-tense, with no code block formatting. Example: "Add dashboard grid layout scaffold".
- Never invent, guess, or assume a version number (vX.X.XX). Use one only when my prompt gives it to you, and then the commit title starts with it, for example "v0.9.04: Short Title". Otherwise commit titles have no version number.
- Never use em dashes or en dashes anywhere: not in code comments, not in commit messages, not in any generated text. Use a comma, colon, or period instead.

# Environment variables: critical gotcha
- The running app (`src/auth.ts`, `src/lib/prisma.ts`) and `prisma/seed.ts` all build their database connection from five separate environment variables: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`. They do NOT read `DATABASE_URL`.
- Prisma CLI commands (`migrate dev`, `migrate deploy`, `migrate reset`) read `DATABASE_URL` from `prisma.config.ts` instead.
- This means a script or command that appears to target one database via `DATABASE_URL` may silently run against a completely different database if `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` are set differently in the active environment.
- Before running any command that writes, seeds, or migrates data, explicitly check and state which actual database the current `DB_HOST`/`DB_NAME` values point to. Never assume `DATABASE_URL` and `DB_NAME` are in sync.
- Never run `prisma/seed.ts` or any destructive script without first confirming the active `DB_NAME` is not the live production database, unless explicitly instructed to target production.
- `prisma/seed.ts` runs only against the dev database: it uses the dev-only guard (`enforceDevGuard` from `scripts/dev-only/lib/guard.ts`), which loads `.env.development.local` (never `.env`) and refuses to run unless `DB_NAME` is exactly `psasync_dev`, `NODE_ENV` is not production, and `--yes` is passed: `npm run seed -- --yes`. It also needs `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` set in the environment: if either is missing or empty, the email isn't an email, or the password breaks the change password rules (`src/lib/password-rules.ts`), it stops with a message naming the problem and exits 1 before it opens a database connection, and it never prints the password. It creates the company TIPINC with that admin, holding the Global Admin role (`setUserRoles`), the password stored only as a bcrypt hash and to be changed on first sign in (`mustChangePassword`). When a user with that email already exists, it is left as is (password and roles unchanged) and nothing is seeded. There is no `prisma.seed` config; `npm run seed` is the only way it runs. An old fixed admin password is still in git history, so any account that ever used it must have its password changed.

# Prisma conventions
- Run `npx prisma format` before every migration.
- When adding a relation between two models that already share another relation, explicitly name it with `@relation("Name")` on both sides, or `prisma format` will error on ambiguous relations.
- Always include the migration name inline in migrate commands, e.g. `npx prisma migrate dev --name add_dashboard_and_widget_models`, never leave it to prompt interactively.

# Project structure
- Prisma schema at `prisma/schema.prisma`.
- API routes under `src/app/api/`, following Next.js App Router conventions (`route.ts` with GET/POST/PATCH/DELETE exports, params as a Promise in dynamic segments).
- Shared components in `src/components/`, organized by feature area (`src/components/inventory/`, `src/components/clients/`, etc).

# API routes
- Every new or changed route handler starts with `const { ctx, response } = await requireAccess(rule?)` from `src/lib/api-access.ts` and returns `response` if set. Use `ctx.companyId` and `ctx.userId`, never the session token's values.
- Ids from the URL go through a scoped loader in `src/lib/scoped-loaders.ts`, never a bare id lookup. A miss returns `notFound()`. Updates and deletes use the matching `*Where` builder so the write itself is company scoped.
- Ids that arrive in a request body (tag ids, location ids, vendor ids, etc.) must be validated against the caller's company before use.
- Use `assertRefs(ctx, { ... })` from `src/lib/scoped-loaders.ts` for body ids: it checks them all in one query per record type, skips empty values, and returns a ready 400 (or null when valid). Add a new key there rather than writing a one off lookup.
- Responses use explicit `select` objects. Errors use the shape `{ error, code? }`.
- An API response never carries a caught error's own message, `String(err)`, or a stack (a database or Prisma error says how the app is built). A route's catch block answers with `userFacingError(err, context)` from `src/lib/user-error.ts`: a `UserError` (one our own code throws with a message written for the user, such as `generateAssetTag`'s missing prefix) keeps its message with a 400, and anything else is the 500 "Something went wrong. Please try again." with one server log line (the error's kind, Prisma code and fields, and the first line of its message, never the values it was called with). Validation messages a route returns on purpose stay as they are. Distributor connection tests store and show only "Connection failed. Check the credentials and try again." (`connectionFailed` in `src/lib/distributors/types.ts`).
- Logging: no `console.log`, `console.info`, or `console.debug` in `src`. A failed outbound call logs one short line with the status (and Graph's error code), never a request URL, a response body, an SDK error object (the Ingram SDK's carries the bearer token), credentials, tokens, email addresses, or pricing.
- Every route declares the permission it needs in the `requireAccess` call itself, for example `requireAccess({ permission: "quotes.edit", message: "You do not have permission to edit quotes" })`, never as a separate check further down. A missing permission is a 403 with code `FORBIDDEN` and a short plain `message`. A record the user may not open is a 404 `{ error: "Not found" }`, the same as one that doesn't exist.
- Reads shared by several pages (pickers, search) use an any-of rule, `permission: ["pages.quotes", "pages.catalog", ...]`, where holding one is enough.
- Every quote route runs the quote view check (VQ) on its URL id: `loadViewableQuote`, or `viewableQuoteWhere` when the route needs its own include, both in `src/lib/scoped-loaders.ts`. A user may open a quote with `pages.quotes` and then only their own, everyone's with `quotes.viewAllUsersQuotes`, or one waiting on an approval they can decide. Lists, totals, and widgets filter with `quoteListWhere`. Writes after the check use `quoteWhere`.
- A quote has no creator field, only its owner (`userId`), so the view rule can't let a creator follow a quote they gave away. Instead the owner a user may set is limited by `mayAssignQuoteTo` in `src/lib/scoped-loaders.ts`: without `quotes.viewAllUsersQuotes` only themselves. `POST /api/quotes` (the New Quote form's Assigned Rep) and `POST /api/quotes/[id]/assign` refuse anyone else with 403 `FORBIDDEN` "You can only assign quotes to yourself" (`SELF_ASSIGN_ONLY_MESSAGE`), checked after VQ on the assign route. The New Quote form and the quotes list's Assign menu offer only the current user to them. view-all holders and Global Admin assign anyone (an active user of the company, else 400 "Invalid user").
- Copying a quote (`POST /api/quotes/[id]/copy`, `quotes.create` plus VQ on the source, the copy owned by the copier) copies only its details and items and requires `clientId` and `contactId` in the body: 400 "A client is required" / "A contact is required" when missing, and `assertRefs` (plain string ids only) for "Invalid client" / "Invalid contact" (the contact must belong to that client). It keeps the title (with " (Copy)"), intro, terms and the default terms box (ticked stores a copy of the current default, like a new quote), the section list, the template link, and every line. It takes the chosen client's payment terms and ship to (`clientQuoteDefaults` in `src/lib/quote-client-defaults.ts`, the same rule the New Quote form uses), a new number and tokens, DRAFT, and a new date only expiry (`expiryDateFromToday` in `src/lib/quote-expiry.ts`, from the template's expiry days when the template still exists, else the company Default Expiry, else 30). It never copies the client, contact, PO number, ship contact name, internal notes, tax rate, flag, status, sends, views, responses, signature, portal comment, held email, approvals, or comments. The Copy action on the quotes list opens `CopyQuoteModal` (`src/components/quotes/`), which picks the contact (and its client) with the New Quote form's `ContactSearchInput`; nothing is created until Create Copy.
- A copy, a new version, and a quote made from a template build their lines with `copiedLineData` in `src/lib/quote-line-copy.ts`, the one list of line fields (every QuoteLineItem field but id, quoteId, and createdAt), read in display order (`COPY_SOURCE_LINE_ORDER`). Bundles and choice groups are tied by name (`bundleName` with `isBundleHeader`, `choiceGroup` with `optionalSelected` as the chosen option), so copying the names keeps children under the new header and options in the new group. Copies and new versions also copy `sections` (the section order, including empty sections). A new line field goes in `copiedLineData` first. Cost comes from the stored source rows, never the request.
- Every sales order route runs the sales order view check (VSO) on its URL id, and every purchase order route the purchase order view check (VPO): `loadViewableSalesOrder` / `viewableSalesOrderWhere` and `loadViewablePurchaseOrder` / `viewablePurchaseOrderWhere` in `src/lib/scoped-loaders.ts`. The line item and attachment loaders there run the same check on their parent order. A user may open an order with the page permission (`pages.salesOrders` / `pages.purchaseOrders`) and then only their own (the order's `userId`, which for an order created when a quote is accepted is the quote's owner) unless they hold `salesOrders.viewAll` / `purchaseOrders.viewAll`. A miss is a 404. Lists and widgets filter with `salesOrderListWhere` / `purchaseOrderListWhere`; writes after the check use `salesOrderWhere` / `purchaseOrderWhere`. A sales order's detail lists only the linked purchase orders the user may open (`purchaseOrderVisibilityWhere` on the include: none without `pages.purchaseOrders`), and returns `_count.purchaseOrders` (all of them) so the page locks the same fields the PATCH does.
- Sales order keys: list and detail need `pages.salesOrders`, create `salesOrders.create`, status `salesOrders.changeStatus`, every other field (notes included), line items, and attachment uploads and deletes `salesOrders.edit`, delete `salesOrders.delete`; comments only need VSO. Purchase orders follow the same pattern with the `purchaseOrders.*` keys, and receiving needs `purchaseOrders.edit`. Generating a purchase order from sales order lines needs `salesOrders.generatePO` and VSO on that sales order; a manual purchase order needs `purchaseOrders.create`, and when it names a `salesOrderId` the creator must pass VSO on it (`assertRefs(ctx, { viewableSalesOrderId })`), otherwise a 400 "Invalid sales order" that never says whether the order exists. `GET /api/so-po-settings` needs `settingsSections.salesOrders` (only its settings panel reads it).
- Purchase order "received": a line is inventory tracked when `isInventoryTrackedLine` (`src/lib/po-receiving.ts`, the one rule shared by `POLineItemBuilder` and the line item PATCH) says so: it has a catalog item whose type is PHYSICAL. A tracked line is only received through the receive route, which creates its inventory; the line item PATCH refuses any `received` value on it with 400 "Use Receive to add this item to inventory". Untracked lines (no catalog item, or a non PHYSICAL type) keep the Rcv'd checkbox and Receive All.
- Settings reads: `company-settings`, `microsoft-settings` (never returns the client secret, only `hasClientSecret`), `quote-settings`, `distributors/enabled`, and `distributor-search/preferences` are open to any active user. `notification-settings` needs `settingsSections.notifications` and `approval-workflows` (GET) needs `settingsSections.approvalWorkflows`. `GET /api/users` and `GET /api/roles` are open to any active user for pickers, but email addresses and each role's `permissions` are only returned with `settingsSections.users`. `GET /api/quote-templates` and `GET /api/quote-templates/[id]` take `pages.quotes` or `settingsSections.quotes` (Quote Settings users maintain templates).
- GET routes never write. `GET /api/roles` no longer creates a missing Everyone role: `ensureEveryoneRole` (`src/lib/everyone-role.ts`) runs in the seed and on the writes that need it, POST roles, PUT roles/order, POST users (invite), and PATCH users/[id] when roles change, always outside any transaction (a lost creation race would abort it). `getEffectiveAccess` treats a missing Everyone role as no permissions. (`GET /api/dashboards` still creates the company Default dashboard on first load; there is no other company creation hook for it.)
- Invites (POST /api/users): an email used by a user in the inviter's own company answers "A user with that email already exists"; every other unusable email (another company has it, ignoring case, or it isn't an email) gets the same 400 "This email cannot be used", so an invite never reveals other companies. Roles handed out by an invite and by PATCH users/[id] follow one rule, `assignsRoleAtOrAboveRank` in `src/lib/user-roles.ts`: every role must be below the actor's rank (Global Admin's rank is the highest, so it can assign any role).
- `GET /api/dashboards/widget-data` gives each widget the same visibility as its page. A widget the user may not see answers `200 { type, noAccess: true }` with no data, and the tile shows a no access note.
- Line item cost, and margins worked out from it, is only returned when `canSeeCost(ctx)` (`src/lib/api-access.ts`) is true; otherwise leave it out with `omitCost`, and the UI shows "-" (`canSeeCostWith` in `src/lib/access-check.ts` holds the shared rule). Anything that copies cost into another record reads it from the database, never from the request.
- The same rule covers the catalog and distributor search. `GET /api/catalog` (the picker list) leaves `cost` out of every item unless `canSeeCost(ctx)`, so every consumer types it as `cost?: number` and shows "-" when it is missing. `GET /api/distributor-search` leaves out each offer's `price` and `cost` (both are the company's dealer pricing) on the same condition. `GET /api/catalog/[id]` needs `pages.catalog`, which already implies seeing cost.
- Line item cost is never trusted from the browser. Quote, quote template, sales order, and purchase order line item POSTs set cost with `newLineItemCost` (`src/lib/line-item-cost.ts`): a caller with `canSeeCost` gets the cost they sent when it is a finite number, otherwise the catalog item's stored cost (company scoped), and 0 with no catalog item; a caller without `canSeeCost` always gets the catalog item's cost, or 0. PATCHes only write cost when `mayWriteCost` allows it, so a caller without `canSeeCost` never changes a stored cost. Purchase order lines call the field `unitCost`; omit it with `omitUnitCost`. Sales order and purchase order detail responses leave cost out unless `canSeeCost`, and their pages show "-". `PATCH /api/catalog/[id]` only writes the fields the request includes. List totals worked out from cost (purchase order and vendor purchase order lists) are left as they are.
- Open picker routes, any active user with no rule beyond `requireAccess()`: `GET` on `clients`, `clients/[id]`, `contacts/search`, `catalog` (cost aside), `categories`, `industries`, `contact-tags`, `inventory-custom-fields`, and `vendors`. Forms on other pages (quotes, orders, inventory) read them, so never put a page permission on these.
- Clients: creating and importing needs `clients.create`; editing a client, its contacts, and its locations needs `clients.edit`. Client assets, inventory onboarding, and a site's default container need `pages.inventory`. There is no client DELETE route.
- Catalog, vendors, and inventory routes need their page permission (`pages.catalog`, `pages.vendors`, `pages.inventory`). Catalog DELETE needs `catalog.delete`; inventory asset and stock DELETE need `inventory.delete`; asset Remove needs `pages.inventory` and `inventory.delete`. Catalog order history and a vendor's purchase orders only list the user's own sales or purchase orders (`userId`) unless they hold `salesOrders.viewAll` or `purchaseOrders.viewAll`, the same rule as the order lists.
- Company settings lists: writes to categories, custom fields, and contact tags, and deleting an industry, need `settingsSections.company`. Their settings panels gate on it with `useAccess` and show `SettingsNoAccess`, since the lists themselves load for anyone.
- Any-of rules in this area: `POST /api/industries` takes `settingsSections.company`, `clients.create`, or `clients.edit` (the client forms add an industry inline). `GET /api/inventory-locations` and `GET /api/inventory-locations/own-company` take `pages.inventory` or `purchaseOrders.edit` (purchase order receiving reads them).
- Every route handler under `src/app/api` starts with `const { ctx, response } = await requireAccess(...)` unless its route is on the public list at the top of `scripts/check-route-access.ts` (NextAuth, the CSP report route, the client portal, and the SSO start, lookup, and callback routes). `npm run check:routes` scans every `route.ts` without a database or network and exits 1 if a handler fails this; new routes must pass it. Only routes the forced password change screen needs pass `allowPasswordGate` (`account/password` today).
- Every route that stores or deletes a file in the uploads bucket goes through `src/lib/uploads.ts`, the only place that validates files and talks to S3: `readUpload` / `readUploadFromRequest` (the `file` form field), `storeUpload`, and `deleteStoredObject` / `deleteStoredObjects`. Never call the S3 client anywhere else and never trust the browser's Content-Type or file name.
- Upload rules live in `src/lib/upload-rules.ts`, shared with the browser: the `ATTACHMENT` profile allows PDF, PNG, JPG/JPEG, GIF, WebP, DOC/DOCX, XLS/XLSX, PPT/PPTX, CSV, TXT, and ZIP up to `ATTACHMENT_MAX_BYTES` (4 MB, because uploads pass through a route handler and Vercel caps a function's request body at 4.5 MB); the `LOGO` profile allows PNG, JPG/JPEG, and WebP up to `LOGO_MAX_BYTES` (2 MB). Everything else (HTML, SVG, XML, scripts, executables) is refused. The server also checks the content: magic bytes for PDF, PNG, JPEG, GIF, WebP, ZIP and Office Open XML (ZIP), and legacy Office (OLE); valid UTF-8 with no NUL bytes for CSV and TXT. Refusals are 400 with a plain `error` ("That file type is not allowed", "That file's contents do not match its type", "That file is larger than 4 MB").
- Storage keys never use the file name: `<folder>/<uuid>.<ext>` (`vendors/<id>`, `inventory-assets/<id>`, `sales-orders/<id>`, `purchase-orders/<id>`, `opportunities/<id>`, `vendors/<id>/logo`), and company logos stay flat in `logos/` as `logos/<companyId>-<uuid>.<ext>` so the bucket policy for that prefix keeps applying. The sanitized original name is kept only in the record's display field. Everything except PNG, JPG, GIF, and WebP is stored with `Content-Disposition: attachment`; attachments also get `Cache-Control: private, max-age=86400`. Public URLs keep the format `https://<bucket>.s3.<region>.amazonaws.com/<key>`.
- Every download name goes through `src/lib/content-disposition.ts`: `attachmentDisposition(name, fallback)` (the staff and portal quote PDFs and stored attachments, through `contentDisposition` in uploads.ts) removes control characters, line breaks, and path separators, caps the name at 150 characters with its extension, and writes an ASCII `filename="..."` fallback plus the exact name as RFC 5987 `filename*=UTF-8''...`, so no stored value can break a download or add a header. `quotePdfName` builds a quote PDF's name (also used for the PDF attached to a quote email). Never build a `Content-Disposition` value by hand.
- Number prefixes (`quotePrefix` in quote-settings, `soPrefix` and `poPrefix` in so-po-settings) are letters, digits, and hyphens, 1 to 10 characters (`numberPrefixProblem` in `src/lib/number-prefix.ts`; the defaults Q, SO, and PO follow it), checked only when a prefix changes, so a company whose stored prefix predates the rule can still save its other settings. Anything else is a 400 with a plain message. Stored values are not changed.
- The company Default Expiry (`quoteExpiryDays` in quote-settings) is a whole number of days, 1 or more (`isValidExpiryDays` and `EXPIRY_DAYS_MESSAGE` in `src/lib/quote-expiry.ts`). Left out of the PATCH it is kept; blank, null, 0, negative, fractional, or non number values are a 400 "Default expiry must be a whole number of days, 1 or more". The Quote Settings panel parses its field with `parseExpiryDaysInput`, shows the same message, and sends nothing until it is valid, so clearing the field never saves 0. A stored 0 from before never meant "no expiry": new quotes without a date fall back to 30 days (`settings.quoteExpiryDays || 30`). Stored values are not changed. The New Quote form takes its date from the template's expiry days, not this setting. A quote's expiry (Valid until) counts from when the quote is created (`POST /api/quotes`, the New Quote form, and copy with `expiryDateFromToday`), never from when it is sent: no send path changes `expiresAt`, and a new version keeps the one it was copied from.
- Enum values from a request body are checked with `isEnumValue` before they are written. The quote and quote template line item PATCHes share one recurring interval rule: turning recurring on falls back to MONTHLY, and an interval sent on its own must be a real `RecurringInterval`, otherwise 400 "Invalid recurring interval".
- Deleting an attachment, or a sales order, purchase order, or inventory asset (collect the attachment URLs before the delete), and replacing or removing a logo, calls `deleteStoredObject` after the database write succeeds. It refuses any URL outside the app's bucket and the expected prefix, and is best effort: a failure is logged with the key and never shown to the user. The browser checks type and size first with `checkUploadBasics` (FileUploadZone, the logo pickers); the clients CSV import is limited to 2 MB in the browser and a 4 MB JSON body on the server.
- Customer portal tokens: every route that creates a quote row (new, copy, new version) passes `accessToken` and `internalAccessToken` from `newAccessToken()` (`src/lib/portal-token.ts`, 32 random bytes, base64url). Each version is its own row with its own tokens; old cuid tokens stay valid. Staff responses never include the client `accessToken`: strip it with `withoutCustomerToken` / `withoutPortalTokens`. Only the quotes list and quote detail return `internalAccessToken` (for the internal preview). The UI gets the customer link on demand from `GET /api/quotes/[id]/portal-link` (`quotes.edit` or `quotes.sendEmail`, plus VQ), which also says whether it `opens` yet.
- `POST /api/quotes/[id]/portal-link/regenerate` (`quotes.edit` plus VQ) gives every version of the quote a new client token, so every link already sent stops working at once, and adds "[Customer link regenerated by NAME]" to the top of that version's internal notes. The quote detail page has a Regenerate Customer Link button for users with `quotes.edit`.
- Every portal route starts with `resolvePortalAccess(token, "view" | "act")` from `src/lib/portal-access.ts`, the one place the portal rules live. A client token opens its version only when it was sent (`sentAt`) and its status is in `CLIENT_VIEWABLE_STATUSES` (SENT, VIEWED, ACCEPTED, DECLINED, EXPIRED); a never sent revision's token opens the family's latest sent version, as before. Unknown, malformed, replaced, never sent, and moved back to draft links all get the same 404 `{ error: "This link is no longer valid", code: "LINK_INVALID" }`. Expiry is worked out by `isPastExpiry` in `src/lib/quote-expiry.ts`: an `expiresAt` of exactly midnight UTC (a date from the date input) is valid through the end of that calendar day in `PORTAL_EXPIRY_TIME_ZONE` (America/New_York until companies have a time zone setting), and one with a real time is compared as is. Show the date with `formatValidUntil`. Once expired (or with status EXPIRED) every portal route answers 410 `QUOTE_EXPIRED`, and GET returns only the company's branding; `expiresAt` null never expires. `VIEW_AFTER_EXPIRY_STATUSES` (ACCEPTED) keeps GET and pdf working after expiry with every action refused. Accept, decline, comment, and line item changes need a status in `AWAITING_RESPONSE_STATUSES` (SENT, VIEWED). The internal token is a staff preview of the newest version: GET, comments GET, and pdf only, ignoring expiry, never marking the quote viewed or notifying anyone. It needs a signed in user (`internalPreviewViewer` in `src/lib/portal-access.ts`: `auth()` plus `getEffectiveAccess`; a deactivated user, a missing session, or a user on a temporary password counts as not signed in) who may open that quote under VQ in the quote's own company. No session answers 401 `{ error: "Sign in to PSAsync to view this internal preview.", code: "SIGN_IN_REQUIRED" }` with no quote data, and the portal page shows that message with a Sign in link to `/login` (the login page always goes on to the dashboard, so the preview link is opened again from there); anyone else gets the same 404 as an unknown link. These refusals never count toward the IP limiter. The internal token is only sent to staff (the quotes list and quote detail) and never rotated by regenerate. Customer tokens are unaffected. Public responses still select through `src/lib/portal-public.ts`.
- Portal accept and decline decide in one conditional write (`updateMany` on the quote with its status still in `AWAITING_RESPONSE_STATUSES`); the request that loses a race to another response gets 400 "This quote has already been responded to" (`alreadyRespondedResponse`), and only the winner notifies the rep and (for an accept) creates the sales order. `createSalesOrderFromAcceptedQuote` also returns an existing sales order for the quote, and `SalesOrder.quoteId` is unique.
- Each customer link has per link limits on the expensive portal work (`SUBJECT_LIMITS` in `src/lib/rate-limit.ts`, counted with `consumeSubject`): 20 PDF downloads (`portal-pdf`) and 30 comments (`portal-comment`) per hour, every request counted, the signed in internal preview never. A blocked request is 429 with `Retry-After` and "This quote link has been used too often. Please try again in N minutes." (`linkLimitedResponse`); the portal page shows it as a toast on the PDF button (which downloads with a fetch) and as the comment box's message.
- Superseded versions: a version the customer opens is superseded (`isSupersededVersion` in `src/lib/portal-access.ts`) when it is not the family's active version (`isActive`, moved by every send and by reactivate) and a different version is active and was sent. It still opens and its PDF downloads, but accept, decline, comments, and line item changes answer 400 `SUPERSEDED` "A newer version of this quote has been sent", checked after every other rule. The portal GET returns `superseded` and the page shows "A newer version of this quote is available. Please use the latest link you received." instead of Accept, Decline, and the message box. A family whose active version was never sent (a reactivated draft) supersedes nothing. Only a link to a version that isn't active costs the extra query. Opening a superseded version never records a view: the portal GET moves SENT to VIEWED and sends the QUOTE_VIEWED notification only for a client token that isn't superseded (the internal preview never does). Sending a newer version only clears `isActive` on the older ones, which keep their status, so an older version can still be SENT.
- Portal input: every customer field is checked with the helpers and limits in `src/lib/portal-input.ts` (shared with the portal page's inputs): decline reason and comment up to `PORTAL_DECLINE_REASON_MAX` / `PORTAL_COMMENT_MAX` (2000), signer name, typed signature, PO number, and ship to fields up to `PORTAL_NAME_MAX` (200), a drawn signature only as a PNG data URL up to `PORTAL_DRAWN_SIGNATURE_MAX`, `termsAgreed` exactly true, `optionalSelected` a boolean, and quantity a whole number from 0 to `PORTAL_QUANTITY_MAX`. Text is trimmed; anything else is a 400 with a plain message. A new portal field gets a limit there first.
- Rich HTML fields (today the quote terms: `Quote.terms`, `QuoteTemplate.terms`, and the company default `CompanySettings.quoteTerms`, and timeline notes, `TimelineEntry.body`, through `src/lib/timeline.ts`) are sanitized with the shared helper in `src/lib/sanitize-terms.ts` both on save and on the way out, and are never rendered raw. Writes use `termsForStorage`; responses use `withSafeTerms` / `termsToDisplayHtml` (the staff quote mappers in `src/lib/portal-token.ts`, `toPortalQuote` in `src/lib/portal-public.ts`, the template and quote settings routes, and `buildQuotePdfHtml` all do this already). The allowlist is exactly what the terms editor (TipTap StarterKit) writes; a new editor extension or a new rich field updates the helper first. A value with no tags or entities is older plain text and is shown escaped with its line breaks. `sanitize-html` is server side only: never import it, or `sanitize-terms.ts`, from a client component or a file one imports. Pages render terms with `dangerouslySetInnerHTML` only from a sanitized API response.
- Which terms a quote or template shows is decided in one place, `resolveQuoteTerms` / `resolveTemplateTerms` in `src/lib/quote-terms.ts`, and its output always passes through the sanitizer. A quote's terms are FROZEN (`isTermsFrozen`, the only definition, with `notFrozenWhere` as its database condition) when `sentAt` is set or its status is anything other than DRAFT and PENDING_APPROVAL (SENT, VIEWED, ACCEPTED, DECLINED, and EXPIRED are frozen). Nothing clears `sentAt`, so a sent quote moved back to DRAFT stays frozen and a new version is the way to change its terms. A quote not frozen with `useDefaultTerms` ticked shows the CURRENT company default (`CompanySettings.quoteTerms`); every frozen quote, and every quote with the box unticked, shows its stored `terms`. Staff quote detail returns `termsFrozen` and the quote page shows terms read only from it, never its own check. Templates are never sent, so they follow the default whenever the box is ticked. Staff quote and template responses return `effectiveTerms` (what to show) and `termsDifferFromDefault` (ticking would replace custom text, so the page asks first with `confirmDialog`) next to the stored `terms` the editor uses; `toPortalQuote` returns the effective terms as `terms` and never the flag or the default; every PDF (staff, portal, and the one attached to an email) gets `effectiveTerms` from the resolver. Pages never decide on their own. Any new code that shows terms uses the resolver.
- Freezing copies the default in: every path that moves a quote into a frozen state (`send`, `send-email`, `completeApprovedQuote` in `src/lib/quote-approval.ts`, and the `status` route for every status past DRAFT and PENDING_APPROVAL, which the bulk Mark Lost and Mark Expired actions also use) works out `termsFreezeFor` once, builds any email's PDF from it (`termsFreeze` on `sendQuoteEmail`), and writes it with `applyTermsFreeze` inside the transaction that changes the status, a conditional write on the quote not being frozen yet so running it twice never replaces the first text. Portal accept, decline, viewed, and expiry marking only ever start from a quote that is already frozen (sent), so they need no freeze. Any new code that changes a quote's status out of DRAFT or PENDING_APPROVAL freezes the same way. A held email freezes when the approval completion actually sends it.
- Approval workflows are evaluated in one place, `src/lib/approval-workflows.ts` (`matchingWorkflows` / `loadMatchingWorkflows`, `approvalFingerprint`, `approvalsStillGranted`, `approvalsCoverQuote`), used by `send`, `send-email`, the `status` route, and `completeApprovedQuote`. The `status` route refuses a move from DRAFT or PENDING_APPROVAL to SENT, VIEWED, or ACCEPTED with 400 "This quote needs approval before it can be changed to this status. Use Send Quote to request approval." (`APPROVAL_REQUIRED`) unless every matching workflow is already APPROVED with a matching fingerprint (the rule send-email uses to send directly). DECLINED and EXPIRED (the bulk Mark Lost and Mark Expired actions) are always allowed, moves from a status already past DRAFT and PENDING_APPROVAL are unchanged, and with no matching workflow the route behaves as before. The quote pages show a refused status change, and the bulk actions change each quote on its own and report how many couldn't be changed.
- Requesting approval records `requestedFingerprint` in `pendingEmailPayload` (with the held email from send-email, or on its own from send). When the last approval is granted, `completeApprovedQuote` claims the quote (PENDING_APPROVAL to DRAFT, one conditional write, so two approvers never both send) and checks `approvalsCoverQuote` before sending anything: if the fingerprint changed since the request, or a workflow that matches now isn't APPROVED, the quote stays in DRAFT, the held email is kept with `approvalStale` and `lastSendError` (and without `approvedFingerprint`, so the approvals no longer count and sending again requests approval again, which resets them to PENDING), the owner gets a notification, and the approve route answers 200 with `stale: true` and the warning "This quote changed after approval was requested, so it was not sent. The owner must request approval again." A hold recorded before the fingerprint existed is only re-checked against the workflows. Nothing else changes when the quote is unchanged. Saves go through `termsPatchData`: ticking the box stores a copy of the current default, unticking without new text stores a copy so the editor starts from it, and terms sent while the box is ticked are replaced by the default copy. A quote PATCH never changes the terms or the box once `sentAt` is set. Copies and new versions keep the stored terms and the box, and a new quote takes the box from the request, then the template, then ticked.
- The SSO callback (`src/app/api/sso/callback/route.ts`) compares the `tid` claim of the id token from Microsoft's token endpoint with the company's saved tenant, ignoring case, before linking anything (`checkSsoTenant` in `src/lib/sso-tenant.ts`), and refuses a mismatch with `?error=wrong_tenant`. A tenant saved as a domain name instead of a GUID can't be compared and is skipped; the Microsoft settings panel warns Global Admins when SSO is on with such a tenant. Signing in never changes the owner (`connectedByUserId`) of a mailbox another user connected.
- SSO user matching (`src/lib/sso-match.ts`): a user already linked (`User.microsoftId`, the id token's `oid`, which equals Graph's `/me` id) signs in by that link. A first sign in links the one company user whose stored email equals, ignoring case, the id token's `preferred_username` (the sign in name, UPN, `firstSignInName`) and nothing else: never the `email` claim or the Graph `mail` attribute, which a directory admin can set to anything. A first sign in without a usable `preferred_username` is refused with `?error=no_account_found` and a log line that holds no address. Two users with the same address in different case match nobody. A Microsoft account already linked to any other user, or a user already linked to a different Microsoft account, is refused with `?error=account_already_linked` and nothing is relinked. Graph's `mail` (or `userPrincipalName`) is still the address the mailbox connection is saved under.
- The Settings page lists only the panels the user may use (`PANEL_PERMISSION` in `src/app/dashboard/settings/page.tsx`), shows `NoAccess` without `pages.settings` or any usable panel, and `SettingsNoAccess` for a `?panel=` link to a hidden one. The Microsoft panel is open to anyone who can open Settings, for their own mailbox; the app credentials, SSO, and other users' mailboxes need `settingsSections.integrations`.
- Client components get the signed in user's access from `useAccess()` (`src/components/AccessProvider.tsx`, filled by the dashboard layout) and use it only to hide or disable UI. Pages the user can't open show `NoAccess` (`src/components/NoAccess.tsx`).
- A new permission key is registered in every one of these places, or saving a role that has it fails: `DEFAULT_PERMISSIONS` in `src/app/api/roles/route.ts`, the Everyone defaults in `src/lib/everyone-role.ts`, `BOOLEAN_SECTIONS` in `src/lib/role-permission-rules.ts`, the `RolePermissions` type in `src/lib/permissions.ts`, `buildGlobalAdminPermissions` in `src/lib/global-admin-role.ts`, and the matching labels list in `src/components/settings/RolesPermissionsPanel.tsx`. A removed key goes in `LEGACY_KEYS` in `role-permission-rules.ts` so older roles still save.

# Opportunities
- Models (`prisma/schema.prisma`): `Opportunity` (number unique per company, title, a required client and a required contact of that client, an optional `clientLocationId` (a location of that client, ON DELETE SET NULL, indexed), `ownerId` where null means unassigned, a required stage, an optional type, `source` MANUAL/TICKET/QUOTE defaulting to MANUAL, `expectedValue` Decimal(12, 2), `expectedCloseDate`, `stageChangedAt`, `closedAt`, `createdById`), `OpportunityStage` (name, `category` OPEN/WON/LOST, `sortOrder`, `winProbability` a whole number 0 to 100), `OpportunityType` (name, `sortOrder`), `OpportunityAttachment` (the same fields and scoping as `SOAttachment`), and one `OpportunitySettings` row per company (`prefix`, default OPP; `nextNumber`, the numbering counter; `quoteSentStageId`, the OPEN stage a sent quote moves its opportunity to, used from Branch 3). `Quote`, `SalesOrder`, and `PurchaseOrder` have a nullable `opportunityId` (ON DELETE RESTRICT). `sourceTicketId` is a plain string with no relation until tickets exist (Phase 2 or 3 adds it); no route accepts it from a request yet. The old plain text `Opportunity.notes` column is gone (removed while opportunities existed only on the dev database); notes live on the timeline.
- Defaults are lazy: `ensureOpportunityDefaults(companyId)` (`src/lib/opportunity-defaults.ts`) creates the stages New (OPEN 10), Qualified (OPEN 25), Proposal (OPEN 50), Negotiation (OPEN 75), Won (WON 100), Lost (LOST 0), the types New Business, Upsell, Renewal, and the settings (prefix OPP, quote sent stage Proposal) when the company has no settings row yet. Every opportunity, stage, type, and settings route calls it first; nothing else does (not company creation, not a migration). It is race safe because the settings row is the claim: one transaction inserts it with ON CONFLICT DO NOTHING on the unique `companyId` and only the inserter creates the rest, while a racing request waits on that index and then finds the row.
- Numbers look like OPP-2026-0001 (`formatOpportunityNumber`, the quote number format: prefix, year, a sequence of at least four digits that keeps counting across years). `takeOpportunityNumber` takes the sequence with one atomic increment of `OpportunitySettings.nextNumber` inside the create's transaction, so two creates never share a number and a failed create gives it back. (Quote numbers count rows and have no such protection.)
- Permission keys: `pages.opportunities` (list and open opportunities, read stages, types, and settings), `opportunities.create`, `opportunities.edit` (fields and attachments), `opportunities.delete`, `opportunities.viewAll` (everyone's opportunities, any owner), and `settingsSections.opportunities` (stage, type, and settings writes; also reads them). Everyone and new roles start without them; Global Admin has them all.
- Visibility (VOP, `opportunityVisibilityWhere` / `loadViewableOpportunity` / `viewableOpportunityWhere` / `opportunityListWhere` in `src/lib/scoped-loaders.ts`): with `pages.opportunities`, a user opens their own and unassigned opportunities, or all with `opportunities.viewAll`. Anything else is a 404 on every route, attachments included; lists filter the same way. Writes after the check use `opportunityWhere`.
- Owner rule (`mayAssignOpportunityTo`): without `opportunities.viewAll` the owner can only be the caller or null (unassigned); anything else is 403 `FORBIDDEN` "You can only assign opportunities to yourself or leave them unassigned", checked before `assertRefs`. POST makes the caller the owner unless the body names one. The owner must be an active user of the company (400 "Invalid user").
- Routes: `GET/POST /api/opportunities` (list: `stageId`, `typeId`, `clientId`, `ownerId` or `unassigned`, `closeFrom`/`closeTo` on the expected close date with the last day included, `q` over title, number, and client name; newest first and unpaged like the quotes list; query ids go through `assertRefs`), `GET/PATCH/DELETE /api/opportunities/[id]`, `GET/POST /api/opportunities/[id]/attachments` and `DELETE .../attachments/[attachmentId]` (mirroring the sales order attachment routes), `GET/POST /api/opportunity-stages`, `PATCH/DELETE /api/opportunity-stages/[id]`, `POST /api/opportunity-stages/reorder` (every stage id in the new order; a list that isn't exactly the company's stages is 409), `GET/POST /api/opportunity-types`, `PATCH/DELETE /api/opportunity-types/[id]`, `POST /api/opportunity-types/reorder` (every type id in the new order, the same rule and 409 as the stage reorder), `GET /api/opportunities/[id]/related` (the Related panel, below), and `GET/PATCH /api/opportunity-settings`. Stage, type, and settings reads take `pages.opportunities` or `settingsSections.opportunities`. Body ids use the `assertRefs` keys `opportunityStageId` and `opportunityTypeId`; the contact must belong to the client (a client or contact change is checked as a pair), otherwise 400 "Invalid contact".
- Stage changes (`stageChangeData` in `src/lib/opportunity-rules.ts`): moving to another stage sets `stageChangedAt`, moving into a WON or LOST stage sets `closedAt`, and moving into an OPEN one clears it. A create into a closed stage sets `closedAt` too. POST defaults to the first OPEN stage by `sortOrder`. A stage whose category changes (`PATCH /api/opportunity-stages/[id]`) takes its opportunities with it in the same transaction (`stageCategoryClosedAtUpdate`): into WON or LOST sets `closedAt` to now where it is empty (an earlier close date is kept), into OPEN clears it. The existing category guards run first.
- Delete blocks (409 with a plain message): an opportunity linked to any quote, sales order, or purchase order (`OPPORTUNITY_LINKED`); a stage used by an opportunity (`STAGE_IN_USE`), the last stage of its category (`LAST_STAGE_IN_CATEGORY`), or the quote sent stage (`QUOTE_SENT_STAGE`); a type used by an opportunity (`TYPE_IN_USE`). A stage's category change is refused when it would leave its old category empty, or move the quote sent stage out of OPEN. `quoteSentStageId` must be an OPEN stage of the company (or null). A link or use that lands between the check and the delete is caught as the database's P2003 and answered with the same 409. Stage, reorder, and settings writes run in `withOpportunitySettingsLock` (it locks the settings row, and a refusal rolls back, so a refused request changes nothing). The prefix follows `numberPrefixProblem`, checked only when it changes.
- Deleting an opportunity deletes its attachment rows (cascade) and then, best effort, their files under the upload prefix `opportunities/<id>/` (`deleteStoredObjects`). Uploads store at `opportunities/<id>/<uuid>.<ext>` with the `ATTACHMENT` profile.
- Responses select through `src/lib/opportunity-selects.ts` (users by id and name only, never email). `expectedValue` comes back as text, for example "1250.5". The detail select (GET, PATCH, and POST responses, so only users who may open the opportunity) also carries its Client details: the client's `phone`, its primary location (`locations` where `isPrimary`, one) and `mainBillingLocation` (name and address fields only), the opportunity's `clientLocation` (name and address), and the contact's `title`, `email`, `phone`, and `mobile`. When the opportunity has no location the page shows the client's main location instead. Nothing else from the client record is returned, and the list select never carries them. - Screens: the sidebar shows Opportunities (after Quotes) with `pages.opportunities`. `/dashboard/opportunities` and `/dashboard/opportunities/[id]` are server components that check `pages.opportunities` on the session (`checkAccess`) and render only `NoAccess` without it, the same result as other guarded pages; Settings > Opportunity Settings (`OpportunitySettingsPanel`) is listed with `settingsSections.opportunities` through `PANEL_PERMISSION`. The client pages live in `src/components/opportunities/`, and their shared rules in `src/lib/opportunity-view.ts` (no React or database imports).
- URL: the Opportunities page keeps its view and filters in the query string (`readOpportunityUrl` / `opportunityUrlQuery`), so a refresh or a shared link opens the same page: `view=list` (the board is the default and leaves it out), `q` (title, number, or client), `owner` (`me`, `unassigned`, or a user id; any user only with `opportunities.viewAll`), `client`, `type`, `closeFrom` and `closeTo` (YYYY-MM-DD), and `stage` (list only; the board's columns are the stages). Unusable values fall back to the default. `opportunityApiQuery` maps them to the list route's parameters (`me` becomes the user's id).
- Board: one column per stage in `sortOrder`, fixed width, scrolling sideways (`boardColumns`). Each header shows the stage, a tinted category pill (`CategoryPill`: Open in brand-primary, Won in success, Lost in danger), the card count, and the total value. Won and Lost columns show only opportunities closed in the last `CLOSED_COLUMN_DAYS` (30) days (one with no `closedAt` counts as older) and link the rest as "N older, view in list" (the list filtered to that stage). Value is `expectedValue` for now; Branch 3 switches it to the latest quote total. With `opportunities.edit` a card drags to another column (dnd-kit, the pointer on the whole card or the keyboard from its handle, Left and Right jumping between columns): `moveOpportunityStage` moves it at once, PATCHes `stageId`, and on a failure puts the card back exactly as it was with an error toast.
- List: Number, Title, Client, Contact, Owner, Stage (tinted pill), Type, Value, Expected close, and Updated, fixed widths with sideways scroll, sorted by header click (ascending, descending, back to newest first) like the quotes list. Clicking a row opens the opportunity.
- Location: "main location" means the client's primary location (the first by name if several are marked), else its main billing location, else none; the one rule is `mainClientLocation` in `src/lib/client-main-location.ts`, and `loadClientMainLocationId` (`src/lib/scoped-loaders.ts`) applies it on the server. `POST /api/opportunities` takes an optional `clientLocationId`: left out, the client's main location is saved (null when it has none); null or blank, no location. `PATCH` takes `clientLocationId` (null clears it); `assertRefs` ties it to the opportunity's client (the new one when the client changes, otherwise the kept one), so a location of another client or company is a 400 "Invalid location". The New opportunity dialog's Location select lists the chosen client's locations (`useClientLocations`), starts on the main location (marked "(main)"), and leaves the field out of the request until the user changes it.

# Timeline
- `TimelineEntry` (`prisma/schema.prisma`) is a record's activity history, shared: opportunities use it now, and tickets (a later phase) add their own nullable link and reuse the same model, route pattern (`src/app/api/opportunities/[id]/timeline` and `.../timeline/[entryId]`), helpers (`src/lib/timeline.ts`, server side; `src/lib/timeline-actions.ts`, client safe), and component (`Timeline` in `src/components/timeline/`, which takes the record's timeline URL). Fields: `companyId`, `opportunityId` (nullable, ON DELETE CASCADE), `kind` (`TimelineEntryKind`: NOTE, ACTION, and EMAIL_OUT and EMAIL_IN, unused until the mailbox phase), `authorId` (nullable, ON DELETE SET NULL; null is the system), `body` (NOTE rich text HTML), `action` and `data` (ACTION key and its before and after values, names stored next to ids so an entry reads correctly after a rename or delete), `editedAt`, `createdAt`. Indexes on `companyId` and on (`opportunityId`, `createdAt`).
- ACTION entries are written with `recordTimelineActions` inside the same transaction as the change, by the user who made it. Keys (`TIMELINE_ACTIONS`, read as sentences by `describeTimelineAction`): `created`, `stage_changed`, `owner_changed`, `type_changed`, `client_changed`, `contact_changed`, `title_changed`, `expected_value_changed`, `expected_close_date_changed`, `attachment_added`, `attachment_removed`. For opportunities `opportunityChangeActions` (`src/lib/opportunity-timeline.ts`) compares the opportunity read inside the PATCH's transaction with the saved one and records one entry per field that changed, nothing for a PATCH that changes nothing. A stage's category change (the closedAt update) records nothing, since no opportunity's stage changed. `POST /api/opportunities` records `created` and then, a millisecond later in the same transaction, the optional `initialNote` as the first NOTE.
- Routes: `GET .../timeline` (`pages.opportunities` plus VOP) returns `{ entries, nextCursor }`, newest first (`createdAt`, then `id`), `TIMELINE_PAGE_SIZE` (25) at a time; `?cursor=` must be an entry of the same opportunity (`loadOpportunityTimelineEntry` in `src/lib/scoped-loaders.ts`), otherwise 400 "Invalid cursor". `POST .../timeline` (`opportunities.edit` plus VOP) adds a note by the caller. `PATCH` and `DELETE .../timeline/[entryId]` (`opportunities.edit` plus VOP; an entry of another opportunity or company is a 404) only touch NOTE entries, and only the note's own author, Global Admin included: anything else is 403 `FORBIDDEN` ("Only notes can be edited or deleted" or "You can only edit or delete your own notes"). Editing sets `editedAt`. ACTION and EMAIL entries can never be edited or deleted.
- A note can change its record's stage: `POST .../timeline` takes an optional `stageId` (a string, checked with `assertRefs` key `opportunityStageId`, otherwise 400 "Invalid stage"; the same `opportunities.edit` as the note). In one transaction it moves the opportunity with `stageChangeData` (the PATCH's rule: `stageChangedAt`, `closedAt` set into WON or LOST and cleared into OPEN) and writes ONE entry, the NOTE, with the move in its data as `{ stageChange: { from, to } }` (id, name, and category; read with `noteStageChange` in `src/lib/timeline-actions.ts`), never a separate `stage_changed` entry. A `stageId` equal to the current stage moves nothing and stores no move. Editing the note later changes only its text. The note card shows the move as a tinted pill, for example "New to Qualified".
- Action button bar: `ActionButtonBar` (`src/components/timeline/ActionButtonBar.tsx`) renders rounded pill buttons with an icon from a list of plain, serializable definitions (`ActionButtonDefinition` in `src/lib/timeline-buttons.ts`): `{ id, label, icon, color, opens }`, where `icon` is a name (`note`, `won`, `lost`, `email`, `call`, `meeting`, `task`), `color` a token name (`neutral`, `primary`, `success`, `danger`, `warning`, `info`), and `opens` is `{ kind: "note", stage?: { id?, category? } }` (`presetStageId` picks the stage id, or the first stage of the category in the company's order). The bar wraps onto more lines without shrinking buttons. A later branch stores admin defined buttons for opportunities and tickets and feeds them to the same bar. Opportunities use the fixed `OPPORTUNITY_ACTION_BUTTONS`: Note (no stage), Won (first WON stage), Lost (first LOST stage), only with `opportunities.edit`. On the opportunity page the bar sits in the header and opens the composer through the timeline's handle (`ref` with `openComposer`, `showButtons={false}`, `onComposerChange` for the pressed button; the composer scrolls into view). A button opens the composer inline at the top of the timeline (the note editor, a "Change stage to" select grouped Open, Won, Lost with "No change" first, Post, and Cancel, which asks before discarding typed text); switching buttons keeps the text and changes only the preset stage. `Timeline` takes `buttons`, optional `stages`, and `onPosted` (the opportunity page reloads after a note that moved the stage).
- Note bodies go through the quote terms sanitizer: `readNoteBody` on save (refusing a non string, more than `TIMELINE_NOTE_MAX` characters, or a note with no text after sanitizing, 400 "A note can't be empty") and `toTimelineEntryResponse` on the way out. Authors are returned as id and name only.

# Sessions
- Sign in sessions are JWT cookies with their lifetimes in `src/lib/session-config.ts`: idle `SESSION_IDLE_SECONDS` (7 days, `session.maxAge`), refresh `SESSION_REFRESH_SECONDS` (1 day), and an absolute cap `SESSION_ABSOLUTE_SECONDS` (30 days from signing in).
- Auth.js only re-issues the cookie (moving its idle expiry forward) when `/api/auth/session` is fetched; `auth()` in pages and API routes never renews it. `SessionKeepAlive` (mounted by the dashboard layout) fetches it at most once per refresh period per browser, on load and hourly, so active users aren't signed out at 7 days.
- The jwt callback in `src/auth.ts` runs `sessionAfterCap`: sign in (password and SSO) stamps `signedInAt`; a token without it (issued before the cap) takes its `iat`, its last issue time, once; past the cap the callback returns null, so `auth()` returns null, the dashboard redirects to `/login`, API routes answer 401, and the cookie is cleared where Auth.js can set cookies. No database query is added. A deactivated user is still handled by the session callback (`session.user` becomes null).
- Deactivated and deleted users depend on next-auth's server side wrapper (`getSession` in `node_modules/next-auth/lib/index.js`), which builds the session as `{ user: user ?? token, ...session }`. That is why the session callback returns `user: null` instead of deleting `user`: a missing user would make `auth()` return the raw JWT as the user. Since 5.0.0-beta.32, `auth()` also returns null when Auth.js answers with an error (a broken configuration) instead of the error object. Every caller checks `session?.user` (or its `id`), never only that `auth()` returned something.
- `npm run check:auth` (`scripts/check-auth-session.ts`, no database or network) guards this. It runs the real `src/auth.ts` and the installed next-auth with only the database faked, calls the real `auth()` and `requireAccess()` inside a Next request scope, and checks that a deactivated or deleted user gets a session with `user: null` and a 401, that the wrapper still fills a missing user from the token, that a token past the absolute cap gets null and a cleared cookie, that a missing secret gets null, and that cookie names and attributes (`__Secure-` and `__Host-` on https, HttpOnly, SameSite=Lax), the credentials redirect, and the lockout code are unchanged. Exit 0 pass, 1 a check failed, 2 the harness broke.

# Rate limiting
- `src/lib/rate-limit.ts` limits public entry points by IP, counting failures only, in fixed windows stored in the `rate_limits` table (`RateLimit` model) with one `INSERT ... ON CONFLICT DO UPDATE` per failure. The IP is never stored: rows hold sha256 of `key:ip`. Rows older than two days are deleted by the limiter itself, at most every five minutes per instance.
- Keys and limits are `RATE_LIMITS`: `login` (wrong passwords and unknown emails, 20 per 15 minutes, checked with `isBlocked` before each attempt; a blocked IP gets the sign in code `ipblocked_N` and "Too many attempts from your network. Try again in N minutes." next to the unchanged per account lockout), `portal` (every link that doesn't open, 30 per 15 minutes, counted in `resolvePortalAccess`; a link that opens never touches the table, and an IP this instance already blocked is refused from memory), `sso-lookup` (every call, 30 per 15 minutes), and `csp-report` (every report, 300 per 15 minutes). A refusal is 429 with `Retry-After` and `{ error, code: "RATE_LIMITED", retryAfterSeconds }` (`rateLimitedResponse`).
- Fail open: any error (the table not migrated yet, a database error, a timeout over two seconds) lets the request through and logs at most one warning line per five minutes, without the IP. Success never writes.
- `getClientIp` reads the first `x-forwarded-for` entry (Vercel sets it), then `x-real-ip`. No usable IP, which includes loopback addresses in local development and the dev-only scripts, skips limiting entirely.
- Adding a key: add it to `RATE_LIMITS`, call `recordFailure(key, getClientIp(req))` on its failure path, and either check `isBlocked` before the attempt or answer `rateLimitedResponse` when `recordFailure` reports blocked.
- Per subject limits count every request instead of failures: `consume(key, subject, limit, windowMs)` (or `consumeSubject` with a `SUBJECT_LIMITS` rule) runs the same fixed window upsert with the subject (a customer link's token) hashed with the key like an IP, one upsert per request, failing open with the same warning line. Today: `portal-pdf` and `portal-comment` (see the portal rules above).

# Security headers
- `next.config.ts` `headers()` applies `securityHeaders` from `src/lib/security-headers.ts` to every route: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` plus an enforced `Content-Security-Policy: frame-ancestors 'none'` (nothing frames the app; PDFs download as attachments), `Permissions-Policy` turning off camera, microphone, geolocation, and payment, and `Reporting-Endpoints`. HSTS is left to Vercel. There is no proxy (middleware) file.
- `images.localPatterns` in `next.config.ts` limits the image optimizer (`/_next/image`) to `/icon.png`, the only file `next/image` shows (sidebar and Updates page); any other url gets a 400. Using `next/image` for another local file means adding its path there (in development a `src` that doesn't match throws). `remotePatterns` stays unset.
- The Content-Security-Policy (`buildCsp`, every source explained there) is sent as `Content-Security-Policy-Report-Only` while `CSP_MODE` is "report-only"; setting it to "enforce" sends the same policy as `Content-Security-Policy`. It is static, so it allows `'unsafe-inline'` scripts and styles; a new external origin (a CDN, an image host) goes into `buildCsp` first.
- Browsers post violations to `POST /api/csp-report` (public, `csp-report` rate limit), which reads at most 10 KB, logs one line `CSP violation: directive=... blocked=<origin> page=<path>` (portal tokens shown as `[token]`), stores nothing, never echoes the report, and answers 204.
- `npm run check:headers` (`scripts/check-headers.ts`, no database or secrets; `-- --base-url <url>`, default `http://localhost:3000`) fetches the login page, `/dashboard` (expects a redirect), `/api/users` (401), a portal page and API route, and posts a sample report (204), and checks every header. Exit 1 on any failure, 2 if the app can't be reached.
