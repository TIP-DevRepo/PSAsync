# Verification before calling a task done
Run `npm run lint` and `npm run build` before considering a change complete. Fix errors these surface rather than leaving them for the user to find. A change that adds or edits an API route also runs `npm run check:routes`, which must pass. An upgrade of `next`, `next-auth`, `@auth/core`, or `@auth/prisma-adapter` also runs `npm run check:auth`, which must pass (see Sessions).
- `npm run lint` ignores `src/generated/**` (the Prisma client `prisma generate` writes, set in `eslint.config.mjs`), so its count is only our own code. Never lint or edit the generated client.

# Package manager
This repo uses npm exclusively (`package-lock.json` is the source of truth). Never introduce a `yarn.lock` or `pnpm-lock.yaml`, and don't suggest yarn/pnpm commands.

# Dependency versions
Key dependencies are newer than typical training data: Next.js 16.3.8, next-auth 5.0.0-beta.32 (with @auth/core 0.41.3), React 19.2.4, Prisma 7.8. Before using an API from these, check `node_modules/next/dist/docs/` (per AGENTS.md), `node_modules/next-auth`, `node_modules/prisma`, or the installed type defs rather than assuming familiar behavior. APIs have moved between major versions, and next-auth 5 is still a beta whose behavior can change between beta releases.
- Every upgrade of `next`, `next-auth`, `@auth/core`, or `@auth/prisma-adapter` must keep `npm run check:auth` passing. If it fails, read the installed `node_modules/next-auth/lib/index.js` before changing `src/auth.ts` or the check. `@auth/prisma-adapter` pins an exact `@auth/core`, so it moves together with next-auth to keep a single copy installed.

# Scope discipline
Keep changes scoped to what was asked. Don't refactor, rename, or "clean up" unrelated code while fixing a bug or adding a feature. Separate cleanup into its own explicitly-requested change.

# Secrets and config
`.env*` files are gitignored. Never read or write any `.env*` file (`.env`, `.env.local`, `.env.development.local`, etc.) by any means: no `Read`, `cat`, `Get-Content`, `grep`/`Select-String` over them, no `Write`/`Edit`, no shell redirection into them. Never commit them, print their contents, or hardcode values from them into source. If a task needs a new env var, tell the user in your summary which variable to add, to which file, and why. Do not add it yourself.

# Branching and commits (project conventions)
- I create and switch branches myself and name them `feature/*` or `bugfix/*`. Claude Code works on whichever branch is currently checked out and never creates or switches branches. If the checked out branch looks wrong for the task (for example `main` or `dev`), stop and ask me before making any changes.
- Branch naming: `feature/short-description` for new features, `bugfix/short-description` for bug fixes.
- Commit titles are plain, short, and present-tense, with no code block formatting. Example: "Add dashboard grid layout scaffold".
- Never invent, guess, or assume a version number (vX.X.XX). Use one only when my prompt gives it to you, and then the commit title starts with it, for example "v0.9.04: Short Title". Otherwise commit titles have no version number.
- Never use em dashes or en dashes anywhere: not in code comments, not in commit messages, not in any generated text. Use a comma, colon, or period instead.

# Environment variables: critical gotcha
- The running app (`src/auth.ts`, `src/lib/prisma.ts`) and `prisma/seed.ts` all build their database connection from five separate environment variables: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`. They do NOT read `DATABASE_URL`.
- Prisma CLI commands (`migrate dev`, `migrate deploy`, `migrate reset`) read `DATABASE_URL` from `prisma.config.ts` instead.
- This means a script or command that appears to target one database via `DATABASE_URL` may silently run against a completely different database if `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` are set differently in the active environment.
- Before running any command that writes, seeds, or migrates data, explicitly check and state which actual database the current `DB_HOST`/`DB_NAME` values point to. Never assume `DATABASE_URL` and `DB_NAME` are in sync.
- Never run `prisma/seed.ts` or any destructive script without first confirming the active `DB_NAME` is not the live production database, unless explicitly instructed to target production.
- `prisma/seed.ts` runs only against the dev database: it uses the dev-only guard (`enforceDevGuard` from `scripts/dev-only/lib/guard.ts`), which loads `.env.development.local` (never `.env`) and refuses to run unless `DB_NAME` is exactly `psasync_dev`, `NODE_ENV` is not production, and `--yes` is passed: `npm run seed -- --yes`. It also needs `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` set in the environment: if either is missing or empty, the email isn't an email, or the password breaks the change password rules (`src/lib/password-rules.ts`), it stops with a message naming the problem and exits 1 before it opens a database connection, and it never prints the password. It creates the company TIPINC with that admin, holding the Global Admin role (`setUserRoles`), the password stored only as a bcrypt hash and to be changed on first sign in (`mustChangePassword`). When a user with that email already exists, it is left as is (password and roles unchanged) and nothing is seeded. There is no `prisma.seed` config; `npm run seed` is the only way it runs. An old fixed admin password is still in git history, so any account that ever used it must have its password changed.

# Prisma conventions
- Run `npx prisma format` before every migration.
- When adding a relation between two models that already share another relation, explicitly name it with `@relation("Name")` on both sides, or `prisma format` will error on ambiguous relations.
- Always include the migration name inline in migrate commands, e.g. `npx prisma migrate dev --name add_dashboard_and_widget_models`, never leave it to prompt interactively.
- Never run database queries in parallel inside an interactive transaction (`$transaction(async (tx) => ...)`): no `Promise.all` (or anything else that starts two at once) on `tx` calls, in a route or any helper that takes a `tx`. Await them one after another. A transaction has one connection and pg runs one query at a time on it; overlapping ones log "Calling client.query() when the client is already executing a query is deprecated" (a later pg refuses them). Prisma itself sends the reads for a select with several relations at once, so `src/lib/prisma.ts` wraps its driver adapter with `withSerialTransactions` (`src/lib/serial-transactions.ts`), which queues every query of a transaction until the one before it answers; queries outside a transaction use the pool and stay parallel. A new `PrismaClient` that runs interactive transactions uses the same wrapper.

# Project structure
- Prisma schema at `prisma/schema.prisma`.
- API routes under `src/app/api/`, following Next.js App Router conventions (`route.ts` with GET/POST/PATCH/DELETE exports, params as a Promise in dynamic segments).
- Shared components in `src/components/`, organized by feature area (`src/components/inventory/`, `src/components/clients/`, etc).

# API routes
- Every new or changed route handler starts with `const { ctx, response } = await requireAccess(rule?)` from `src/lib/api-access.ts` and returns `response` if set. Use `ctx.companyId` and `ctx.userId`, never the session token's values.
- Ids from the URL go through a scoped loader in `src/lib/scoped-loaders.ts`, never a bare id lookup. A miss returns `notFound()`. Updates and deletes use the matching `*Where` builder so the write itself is company scoped.
- Ids that arrive in a request body (tag ids, location ids, vendor ids, etc.) must be validated against the caller's company before use.
- Use `assertRefs(ctx, { ... })` from `src/lib/scoped-loaders.ts` for body ids: it checks them all in one query per record type, skips empty values, and returns a ready 400 (or null when valid). Add a new key there rather than writing a one off lookup.
- Responses use explicit `select` objects. Errors use the shape `{ error, code? }`.
- An API response never carries a caught error's own message, `String(err)`, or a stack (a database or Prisma error says how the app is built). A route's catch block answers with `userFacingError(err, context)` from `src/lib/user-error.ts`: a `UserError` (one our own code throws with a message written for the user, such as `generateAssetTag`'s missing prefix) keeps its message with a 400, and anything else is the 500 "Something went wrong. Please try again." with one server log line (the error's kind, Prisma code and fields, and the first line of its message, never the values it was called with). Validation messages a route returns on purpose stay as they are. Distributor connection tests store and show only "Connection failed. Check the credentials and try again." (`connectionFailed` in `src/lib/distributors/types.ts`).
- Logging: no `console.log`, `console.info`, or `console.debug` in `src`. A failed outbound call logs one short line with the status (and Graph's error code), never a request URL, a response body, an SDK error object (the Ingram SDK's carries the bearer token), credentials, tokens, email addresses, or pricing. A caught error is logged as one line with `errorSummary(err)` (`src/lib/user-error.ts`: its kind, Prisma code and fields, and the first line of its message), never the whole error object.
- PDFs: every PDF (the staff quote PDF, the portal and internal preview PDF, and the PDF attached to a quote email) renders through `renderPdf` (`src/lib/pdf-render.ts`), the only place that launches the headless browser. When the browser can't start or render, it logs one line naming the PDF and the step (`errorSummary`, never the page, a token, or customer data) and returns null: the PDF routes answer `pdfUnavailableResponse()`, 503 `{ error: "We couldn't create the PDF right now. Please try again in a minute.", code: "PDF_UNAVAILABLE" }`, and `sendQuoteEmail` refuses the send before anything goes out (`code: "PDF_UNAVAILABLE"`, which send-email answers with the same 503; a held email keeps the message as its send error). The quote page, the quotes list, and the portal download with `downloadPdf` (`src/lib/download-pdf.ts`, a fetch, never `window.open`), which shows a refusal's message as a toast.
- Every route declares the permission it needs in the `requireAccess` call itself, for example `requireAccess({ permission: "quotes.edit", message: "You do not have permission to edit quotes" })`, never as a separate check further down. A missing permission is a 403 with code `FORBIDDEN` and a short plain `message`. A record the user may not open is a 404 `{ error: "Not found" }`, the same as one that doesn't exist.
- Reads shared by several pages (pickers, search) use an any-of rule, `permission: ["pages.quotes", "pages.catalog", ...]`, where holding one is enough.
- Every quote route runs the quote view check (VQ) on its URL id: `loadViewableQuote`, or `viewableQuoteWhere` when the route needs its own include, both in `src/lib/scoped-loaders.ts`. A user may open a quote with `pages.quotes` and then only their own, everyone's with `quotes.viewAllUsersQuotes`, or one waiting on an approval they can decide. Lists, totals, and widgets filter with `quoteListWhere`. Writes after the check use `quoteWhere`.
- A quote has no creator field, only its owner (`userId`), so the view rule can't let a creator follow a quote they gave away. Instead the owner a user may set is limited by `mayAssignQuoteTo` in `src/lib/scoped-loaders.ts`: without `quotes.viewAllUsersQuotes` only themselves. `POST /api/quotes` (the New Quote form's Assigned Rep) and `POST /api/quotes/[id]/assign` refuse anyone else with 403 `FORBIDDEN` "You can only assign quotes to yourself" (`SELF_ASSIGN_ONLY_MESSAGE`), checked after VQ on the assign route. The New Quote form and the quotes list's Assign menu offer only the current user to them. view-all holders and Global Admin assign anyone (an active user of the company, else 400 "Invalid user").
- Copying a quote (`POST /api/quotes/[id]/copy`, `quotes.create` plus VQ on the source, the copy owned by the copier) copies only its details and items and requires `clientId` and `contactId` in the body: 400 "A client is required" / "A contact is required" when missing, and `assertRefs` (plain string ids only) for "Invalid client" / "Invalid contact" (the contact must belong to that client). It keeps the title (with " (Copy)"), intro, terms and the default terms box (ticked stores a copy of the current default, like a new quote), the section list, the template link, and every line. It takes the chosen client's payment terms and ship to (`clientQuoteDefaults` in `src/lib/quote-client-defaults.ts`, the same rule the New Quote form uses), a new number and tokens, DRAFT, and a new date only expiry (`expiryDateFromToday` in `src/lib/quote-expiry.ts`, from the template's expiry days when the template still exists, else the company Default Expiry, else 30). It never copies the client, contact, PO number, ship contact name, internal notes, tax rate, flag, status, sends, views, responses, signature, portal comment, held email, approvals, comments, or opportunity; the body may name an `opportunityId` for the copy (Quotes and opportunities below). The Copy action on the quotes list opens `CopyQuoteModal` (`src/components/quotes/`), which picks the contact (and its client) with the New Quote form's `ContactSearchInput`; nothing is created until Create Copy.
- A copy, a new version, and a quote made from a template build their lines with `copiedLineData` in `src/lib/quote-line-copy.ts`, the one list of line fields (every QuoteLineItem field but id, quoteId, and createdAt), read in display order (`COPY_SOURCE_LINE_ORDER`). Bundles and choice groups are tied by name (`bundleName` with `isBundleHeader`, `choiceGroup` with `optionalSelected` as the chosen option), so copying the names keeps children under the new header and options in the new group. Copies and new versions also copy `sections` (the section order, including empty sections). A new line field goes in `copiedLineData` first. Cost comes from the stored source rows, never the request.
- Every sales order route runs the sales order view check (VSO) on its URL id, and every purchase order route the purchase order view check (VPO): `loadViewableSalesOrder` / `viewableSalesOrderWhere` and `loadViewablePurchaseOrder` / `viewablePurchaseOrderWhere` in `src/lib/scoped-loaders.ts`. The line item and attachment loaders there run the same check on their parent order. A user may open an order with the page permission (`pages.salesOrders` / `pages.purchaseOrders`) and then only their own (the order's `userId`, which for an order created when a quote is accepted is the quote's owner) unless they hold `salesOrders.viewAll` / `purchaseOrders.viewAll`. A miss is a 404. Lists and widgets filter with `salesOrderListWhere` / `purchaseOrderListWhere`; writes after the check use `salesOrderWhere` / `purchaseOrderWhere`. A sales order's detail lists only the linked purchase orders the user may open (`purchaseOrderVisibilityWhere` on the include: none without `pages.purchaseOrders`), and returns `_count.purchaseOrders` (all of them) so the page locks the same fields the PATCH does.
- Sales order keys: list and detail need `pages.salesOrders`, create `salesOrders.create`, status `salesOrders.changeStatus`, every other field (notes included), line items, and attachment uploads and deletes `salesOrders.edit`, delete `salesOrders.delete`; comments only need VSO. Purchase orders follow the same pattern with the `purchaseOrders.*` keys, and receiving needs `purchaseOrders.edit`. Generating a purchase order from sales order lines needs `salesOrders.generatePO` and VSO on that sales order; a manual purchase order needs `purchaseOrders.create`, and when it names a `salesOrderId` the creator must pass VSO on it (`assertRefs(ctx, { viewableSalesOrderId })`), otherwise a 400 "Invalid sales order" that never says whether the order exists. `GET /api/so-po-settings` needs `settingsSections.salesOrders` (only its settings panel reads it).
- Purchase order "received": a line is inventory tracked when `isInventoryTrackedLine` (`src/lib/po-receiving.ts`, the one rule shared by `POLineItemBuilder` and the line item PATCH) says so: it has a catalog item whose type is PHYSICAL. A tracked line is only received through the receive route, which creates its inventory; the line item PATCH refuses any `received` value on it with 400 "Use Receive to add this item to inventory". Untracked lines (no catalog item, or a non PHYSICAL type) keep the Rcv'd checkbox and Receive All.
- Settings reads: `company-settings`, `microsoft-settings` (never returns the client secret, only `hasClientSecret`), `quote-settings`, `distributors/enabled`, and `distributor-search/preferences` are open to any active user. `notification-settings` needs `settingsSections.notifications` and `approval-workflows` (GET) needs `settingsSections.approvalWorkflows`. `GET /api/users` and `GET /api/roles` are open to any active user for pickers, but email addresses and each role's `permissions` are only returned with `settingsSections.users`. `GET /api/quote-templates` and `GET /api/quote-templates/[id]` take `pages.quotes` or `settingsSections.quotes` (Quote Settings users maintain templates). `GET /api/teams` takes `settingsSections.teams`, `pages.opportunities`, or `pages.settings`; each team's member list only goes to `settingsSections.teams`. With `settingsSections.users`, `GET /api/users` also returns each user's `teams` and `teamRoles`.
- GET routes never write. `GET /api/roles` no longer creates a missing Everyone role: `ensureEveryoneRole` (`src/lib/everyone-role.ts`) runs in the seed and on the writes that need it, POST roles, PUT roles/order, POST users (invite), and PATCH users/[id] when roles change, always outside any transaction (a lost creation race would abort it). `getEffectiveAccess` treats a missing Everyone role as no permissions. (`GET /api/dashboards` still creates the company Default dashboard on first load; there is no other company creation hook for it.)
- Invites (POST /api/users): an email used by a user in the inviter's own company answers "A user with that email already exists"; every other unusable email (another company has it, ignoring case, or it isn't an email) gets the same 400 "This email cannot be used", so an invite never reveals other companies. Roles handed out by an invite and by PATCH users/[id] follow the grant rule (Teams below, `roleGrantProblem` in `src/lib/role-grants.ts`): every role must be below the actor's rank (`assignsRoleAtOrAboveRank`) and grant only permissions the actor holds through their own effective roles (Global Admin passes both). PATCH checks only roles the user doesn't already hold directly, so keeping or removing a role needs no more than the hierarchy rule.
- `GET /api/dashboards/widget-data` gives each widget the same visibility as its page. A widget the user may not see answers `200 { type, noAccess: true }` with no data, and the tile shows a no access note.
- Line item cost, and margins worked out from it, is only returned when `canSeeCost(ctx)` (`src/lib/api-access.ts`) is true; otherwise leave it out with `omitCost`, and the UI shows "-" (`canSeeCostWith` in `src/lib/access-check.ts` holds the shared rule). Anything that copies cost into another record reads it from the database, never from the request.
- The same rule covers the catalog and distributor search. `GET /api/catalog` (the picker list) leaves `cost` out of every item unless `canSeeCost(ctx)`, so every consumer types it as `cost?: number` and shows "-" when it is missing. `GET /api/distributor-search` leaves out each offer's `price` and `cost` (both are the company's dealer pricing) on the same condition. `GET /api/catalog/[id]` needs `pages.catalog`, which already implies seeing cost.
- Line item cost is never trusted from the browser. Quote, quote template, sales order, and purchase order line item POSTs set cost with `newLineItemCost` (`src/lib/line-item-cost.ts`): a caller with `canSeeCost` gets the cost they sent when it is a finite number, otherwise the catalog item's stored cost (company scoped), and 0 with no catalog item; a caller without `canSeeCost` always gets the catalog item's cost, or 0. PATCHes only write cost when `mayWriteCost` allows it, so a caller without `canSeeCost` never changes a stored cost. Purchase order lines call the field `unitCost`; omit it with `omitUnitCost`. Sales order and purchase order detail responses leave cost out unless `canSeeCost`, and their pages show "-". `PATCH /api/catalog/[id]` only writes the fields the request includes. List totals worked out from cost (purchase order and vendor purchase order lists) are left as they are.
- Open picker routes, any active user with no rule beyond `requireAccess()`: `GET` on `clients`, `clients/[id]`, `contacts/search`, `catalog` (cost aside), `categories`, `industries`, `contact-tags`, `inventory-custom-fields`, and `vendors`. Forms on other pages (quotes, orders, inventory) read them, so never put a page permission on these.
- Clients: creating and importing needs `clients.create`; editing a client, its contacts, and its locations needs `clients.edit`. Client assets, inventory onboarding, and a site's default container need `pages.inventory`. There is no client DELETE route.
- Catalog, vendors, and inventory routes need their page permission (`pages.catalog`, `pages.vendors`, `pages.inventory`). Catalog DELETE needs `catalog.delete`; inventory asset and stock DELETE need `inventory.delete`; asset Remove needs `pages.inventory` and `inventory.delete`. Catalog order history and a vendor's purchase orders only list the user's own sales or purchase orders (`userId`) unless they hold `salesOrders.viewAll` or `purchaseOrders.viewAll`, the same rule as the order lists.
- Company settings lists: writes to categories, custom fields, and contact tags, and deleting an industry, need `settingsSections.company`. Their settings panels gate on it with `useAccess` and show `SettingsNoAccess`, since the lists themselves load for anyone.
- Any-of rules in this area: `POST /api/industries` takes `settingsSections.company`, `clients.create`, or `clients.edit` (the client forms add an industry inline). `GET /api/inventory-locations` and `GET /api/inventory-locations/own-company` take `pages.inventory` or `purchaseOrders.edit` (purchase order receiving reads them).
- Every route handler under `src/app/api` starts with `const { ctx, response } = await requireAccess(...)` unless its route is on the public list at the top of `scripts/check-route-access.ts` (NextAuth, the CSP report route, the client portal, the SSO start, lookup, and callback routes, and the two cron routes, quote expiry and ticket auto close, which CRON_SECRET protects instead). `npm run check:routes` scans every `route.ts` without a database or network and exits 1 if a handler fails this; new routes must pass it. Only routes the forced password change screen needs pass `allowPasswordGate` (`account/password` today).
- Every route that stores, reads, or deletes a file in the uploads bucket goes through `src/lib/uploads.ts`, the only place that validates files and talks to S3: `readUpload` / `readUploadFromRequest` (the `file` form field), `storeUpload`, `readStoredObject` (a stored file's bytes, for an email attachment; refuses a URL outside the bucket and prefix like `deleteStoredObject`), `presignedDownloadUrl` (a short lived download link, Private attachments below), and `deleteStoredObject` / `deleteStoredObjects`. Never call the S3 client anywhere else and never trust the browser's Content-Type or file name.
- Upload rules live in `src/lib/upload-rules.ts`, shared with the browser: the `ATTACHMENT` profile allows PDF, PNG, JPG/JPEG, GIF, WebP, DOC/DOCX, XLS/XLSX, PPT/PPTX, CSV, TXT, and ZIP up to `ATTACHMENT_MAX_BYTES` (4 MB, because uploads pass through a route handler and Vercel caps a function's request body at 4.5 MB); the `LOGO` profile allows PNG, JPG/JPEG, and WebP up to `LOGO_MAX_BYTES` (2 MB). Everything else (HTML, SVG, XML, scripts, executables) is refused. The server also checks the content: magic bytes for PDF, PNG, JPEG, GIF, WebP, ZIP and Office Open XML (ZIP), and legacy Office (OLE); valid UTF-8 with no NUL bytes for CSV and TXT. Refusals are 400 with a plain `error` ("That file type is not allowed", "That file's contents do not match its type", "That file is larger than 4 MB").
- Storage keys never use the file name: `<folder>/<uuid>.<ext>` (`vendors/<id>`, `inventory-assets/<id>`, `sales-orders/<id>`, `purchase-orders/<id>`, `opportunities/<id>`, `tickets/<id>`, `vendors/<id>/logo`), and company logos stay flat in `logos/` as `logos/<companyId>-<uuid>.<ext>` so the bucket policy for that prefix keeps applying. The sanitized original name is kept only in the record's display field. Everything except PNG, JPG, GIF, and WebP is stored with `Content-Disposition: attachment`; attachments also get `Cache-Control: private, max-age=86400`. Stored URLs keep the format `https://<bucket>.s3.<region>.amazonaws.com/<key>`; only logos are publicly readable by them.
- Private attachments: every attachment (vendor, sales order, purchase order, inventory asset, opportunity, and ticket) is downloaded only through `GET /api/files/<kind>/<attachmentId>` (`src/app/api/files/<kind>/[attachmentId]/route.ts`, the kinds `vendor`, `sales-order`, `purchase-order`, `inventory-asset`, `opportunity`, `ticket` in `ATTACHMENT_KINDS`, `src/lib/attachment-paths.ts`). Each route runs `requireAccess` with its parent page's permission (`page: "vendors"`, `page: "inventory"`, `pages.salesOrders`, `pages.purchaseOrders`, `pages.opportunities`, `pages.tickets`; the opportunity route also runs `ensureOpportunityDefaults` and `ensureTeamDefaults`, the ticket route `ensureTicketDefaults`), then `attachmentDownloadResponse` (`src/lib/attachment-downloads.ts`), which loads the attachment with `loadDownloadableAttachment` (`src/lib/scoped-loaders.ts`: the parent in the caller's company for vendors and assets, VSO, VPO, VOP, and the ticket view check, never a deleted opportunity or ticket). A miss, another company's, or one the user may not view is the 404 `{ error: "Not found" }`. It answers 302 to `presignedDownloadUrl` with `Cache-Control: no-store`: a presigned GET that works for `DOWNLOAD_LINK_SECONDS` (300, five minutes), computed locally, with the type from the key's extension and the record's file name as `inline` (images and PDFs, `inlineDisposition`) or `attachment` (everything else, and an unknown extension as `application/octet-stream`). A stored URL outside the bucket or the parent's prefix (an old dummy link) is 404 `{ error: "File not available", code: "FILE_NOT_AVAILABLE" }` and never redirected. A presigned link or its signature is never logged.
- Never return or render a raw bucket URL for an attachment. Every API response that holds an attachment maps it with `withDownloadUrl(kind, row)` (drops `fileUrl`, adds `downloadUrl`, the download route; today the five attachment list and upload routes and the purchase order detail GET), and every page links `downloadUrl`. `fileUrl` stays in the database for deletes and server side reads (`readStoredObject` for the opportunity Email action, through the S3 client with the app's credentials, never a public URL). A new attachment kind adds its kind to `ATTACHMENT_KINDS`, a case in `loadDownloadableAttachment`, its route, and the mapping on every response.
- Logos stay public: company logos (`logos/<companyId>-<uuid>.<ext>`) and vendor logos (`vendors/<id>/logo/<uuid>.<ext>`) are loaded by URL in quote PDFs, the customer portal, and the app, so `logoUrl` is returned as is. The bucket policy keeps public read only on `arn:aws:s3:::psasync-uploads/logos/*` and `arn:aws:s3:::psasync-uploads/vendors/*/logo/*` (and the same two on `psasync-uploads-dev`); every other key is private. The app's AWS credentials need `s3:GetObject` on the attachment prefixes (`vendors/*`, `sales-orders/*`, `purchase-orders/*`, `inventory-assets/*`, `opportunities/*`, `tickets/*`) for presigned downloads and email attachments to work, alongside the `s3:PutObject` and `s3:DeleteObject` uploads and deletes already use. A presigned link acts with the signer's permissions, so a missing `s3:GetObject` shows as AccessDenied from S3 after the redirect. `img-src` already allows the bucket origin the redirect lands on.
- Every download name goes through `src/lib/content-disposition.ts`: `attachmentDisposition(name, fallback)` (the staff and portal quote PDFs and stored attachments, through `contentDisposition` in uploads.ts) and `inlineDisposition` (images and PDFs opened through the attachment download routes) removes control characters, line breaks, and path separators, caps the name at 150 characters with its extension, and writes an ASCII `filename="..."` fallback plus the exact name as RFC 5987 `filename*=UTF-8''...`, so no stored value can break a download or add a header. `quotePdfName` builds a quote PDF's name (also used for the PDF attached to a quote email). Never build a `Content-Disposition` value by hand.
- Number prefixes (`quotePrefix` in quote-settings, `soPrefix` and `poPrefix` in so-po-settings) are letters, digits, and hyphens, 1 to 10 characters (`numberPrefixProblem` in `src/lib/number-prefix.ts`; the defaults Q, SO, and PO follow it), checked only when a prefix changes, so a company whose stored prefix predates the rule can still save its other settings. Anything else is a 400 with a plain message. Stored values are not changed.
- The company Default Expiry (`quoteExpiryDays` in quote-settings) is a whole number of days, 1 or more (`isValidExpiryDays` and `EXPIRY_DAYS_MESSAGE` in `src/lib/quote-expiry.ts`). Left out of the PATCH it is kept; blank, null, 0, negative, fractional, or non number values are a 400 "Default expiry must be a whole number of days, 1 or more". The Quote Settings panel parses its field with `parseExpiryDaysInput`, shows the same message, and sends nothing until it is valid, so clearing the field never saves 0. A stored 0 from before never meant "no expiry": new quotes without a date fall back to 30 days (`settings.quoteExpiryDays || 30`). Stored values are not changed. The New Quote form takes its date from the template's expiry days, not this setting. A quote's expiry (Valid until) counts from when the quote is created (`POST /api/quotes`, the New Quote form, and copy with `expiryDateFromToday`), never from when it is sent: no send path changes `expiresAt`, and a new version keeps the one it was copied from.
- Enum values from a request body are checked with `isEnumValue` before they are written. The quote and quote template line item PATCHes share one recurring interval rule: turning recurring on falls back to MONTHLY, and an interval sent on its own must be a real `RecurringInterval`, otherwise 400 "Invalid recurring interval".

It refuses any URL outside the app's bucket and the expected prefix, and is best effort: a failure is logged with the key and never shown to the user. The browser checks type and size first with `checkUploadBasics` (FileUploadZone, the logo pickers); the clients CSV import is limited to 2 MB in the browser and a 4 MB JSON body on the server.

- Every portal route starts with `resolvePortalAccess(token, "view" | "act")` from `src/lib/portal-access.ts`, the one place the portal rules live. A client token opens its version only when it was sent (`sentAt`) and its status is in `CLIENT_VIEWABLE_STATUSES` (SENT, VIEWED, ACCEPTED, DECLINED, EXPIRED); a never sent revision's token opens the family's latest sent version, as before. Unknown, malformed, replaced, never sent, and moved back to draft links all get the same 404 `{ error: "This link is no longer valid", code: "LINK_INVALID" }`. Expiry is worked out by `isPastExpiry` in `src/lib/quote-expiry.ts`: an `expiresAt` of exactly midnight UTC (a date from the date input) is valid through the end of that calendar day in `PORTAL_EXPIRY_TIME_ZONE` (America/New_York until companies have a time zone setting), and one with a real time is compared as is. Show the date with `formatValidUntil`. Once expired (or with status EXPIRED) every portal route answers 410 `QUOTE_EXPIRED`, and GET returns only the company's branding; `expiresAt` null never expires. `VIEW_AFTER_EXPIRY_STATUSES` (ACCEPTED) keeps GET and pdf working after expiry with every action refused. Accept, decline, comment, and line item changes need a status in `AWAITING_RESPONSE_STATUSES` (SENT, VIEWED). The internal token is a staff preview of the newest version: GET, comments GET, and pdf only, ignoring expiry, never marking the quote viewed or notifying anyone. It needs a signed in user (`internalPreviewViewer` in `src/lib/portal-access.ts`: `auth()` plus `getEffectiveAccess`; a deactivated user, a missing session, or a user on a temporary password counts as not signed in) who may open that quote under VQ in the quote's own company. No session answers 401 `{ error: "Sign in to PSAsync to view this internal preview.", code: "SIGN_IN_REQUIRED" }` with no quote data, and the portal page shows that message with a Sign in link to `/login` (the login page always goes on to the dashboard, so the preview link is opened again from there); anyone else gets the same 404 as an unknown link. These refusals never count toward the IP limiter. The internal token is only sent to staff (the quotes list and quote detail) and never rotated by regenerate. Customer tokens are unaffected. Public responses still select through `src/lib/portal-public.ts`.

Staff quote and template responses return `effectiveTerms` (what to show) and `termsDifferFromDefault` (ticking would replace custom text, so the page asks first with `confirmDialog`) next to the stored `terms` the editor uses; `toPortalQuote` returns the effective terms as `terms` and never the flag or the default; every PDF (staff, portal, and the one attached to an email) gets `effectiveTerms` from the resolver. Pages never decide on their own. Any new code that shows terms uses the resolver.
- Freezing copies the default in: every path that moves a quote into a frozen state (`send`, `send-email`, `completeApprovedQuote` in `src/lib/quote-approval.ts`, and the `status` route for every status past DRAFT and PENDING_APPROVAL, which the bulk Mark Lost and Mark Expired actions also use) works out `termsFreezeFor` once, builds any email's PDF from it (`termsFreeze` on `sendQuoteEmail`), and writes it with `applyTermsFreeze` inside the transaction that changes the status, a conditional write on the quote not being frozen yet so running it twice never replaces the first text. Portal accept, decline, viewed, and expiry marking only ever start from a quote that is already frozen (sent), so they need no freeze. Any new code that changes a quote's status out of DRAFT or PENDING_APPROVAL freezes the same way. A held email freezes when the approval completion actually sends it.
- Approval workflows are evaluated in one place, `src/lib/approval-workflows.ts` (`matchingWorkflows` / `loadMatchingWorkflows`, `approvalFingerprint`, `approvalsStillGranted`, `approvalsCoverQuote`), used by `send`, `send-email`, the `status` route, and `completeApprovedQuote`. DECLINED and EXPIRED (the bulk Mark Lost and Mark Expired actions) are always allowed, moves from a status already past DRAFT and PENDING_APPROVAL are unchanged, and with no matching workflow the route behaves as before. The quote pages show a refused status change, and the bulk actions change each quote on its own and report how many couldn't be changed.

When the last approval is granted, `completeApprovedQuote` claims the quote (PENDING_APPROVAL to DRAFT, one conditional write, so two approvers never both send) and checks `approvalsCoverQuote` before sending anything: if the fingerprint changed since the request, or a workflow that matches now isn't APPROVED, the quote stays in DRAFT, the held email is kept with `approvalStale` and `lastSendError` (and without `approvedFingerprint`, so the approvals no longer count and sending again requests approval again, which resets them to PENDING), the owner gets a notification, and the approve route answers 200 with `stale: true` and the warning "This quote changed after approval was requested, so it was not sent. The owner must request approval again." A hold recorded before the fingerprint existed is only re-checked against the workflows. Nothing else changes when the quote is unchanged. Saves go through `termsPatchData`: ticking the box stores a copy of the current default, unticking without new text stores a copy so the editor starts from it, and terms sent while the box is ticked are replaced by the default copy. A quote PATCH never changes the terms or the box once `sentAt` is set. Copies and new versions keep the stored terms and the box, and a new quote takes the box from the request, then the template, then ticked.

Signing in never changes the owner (`connectedByUserId`) of a mailbox another user connected.

A first sign in links the one company user whose stored email equals, ignoring case, the id token's `preferred_username` (the sign in name, UPN, `firstSignInName`) and nothing else: never the `email` claim or the Graph `mail` attribute, which a directory admin can set to anything. A first sign in without a usable `preferred_username` is refused with `?error=no_account_found` and a log line that holds no address. Two users with the same address in different case match nobody. A Microsoft account already linked to any other user, or a user already linked to a different Microsoft account, is refused with `?error=account_already_linked` and nothing is relinked. # Opportunities
- Models (`prisma/schema.prisma`): `Opportunity` (number unique per company, title, a required client and a required contact of that client, an optional `clientLocationId` (a location of that client, ON DELETE SET NULL, indexed), `ownerId` where null means unassigned, a required stage, an optional type, `source` MANUAL/TICKET/QUOTE defaulting to MANUAL, `expectedValue` Decimal(12, 2), `expectedCloseDate`, `stageChangedAt`, `closedAt`, `createdById`, and `teamId`, a team (Teams below; nullable in the database only so the column could be added to existing rows, ON DELETE RESTRICT, indexed, and never null once `ensureTeamDefaults` has run)), `OpportunityStage` (name, `category` OPEN/WON/LOST, `sortOrder`, `winProbability` a whole number 0 to 100), `OpportunityType` (name, `sortOrder`), `OpportunityAttachment` (the same fields and scoping as `SOAttachment`), and one `OpportunitySettings` row per company (`prefix`, default OPP; `nextNumber`, the numbering counter; `quoteSentStageId`, the OPEN stage a sent quote moves its opportunity to, Quotes and opportunities below). `Quote`, `SalesOrder`, and `PurchaseOrder` have a nullable `opportunityId` (ON DELETE RESTRICT). `sourceTicketId` is a plain string with no relation until tickets exist (Phase 2 or 3 adds it); no route accepts it from a request yet. The old plain text `Opportunity.notes` column is gone (removed while opportunities existed only on the dev database); notes live on the timeline.
- Defaults are lazy: `ensureOpportunityDefaults(companyId)` (`src/lib/opportunity-defaults.ts`) creates the stages New (OPEN 10), Qualified (OPEN 25), Proposal (OPEN 50), Negotiation (OPEN 75), Won (WON 100), Lost (LOST 0), the types New Business, Upsell, Renewal, and the settings (prefix OPP, quote sent stage Proposal) when the company has no settings row yet. Every opportunity, stage, type, and settings route calls it first; nothing else does (not company creation, not a migration). Every opportunity route (and the sidebar counts) also calls `ensureTeamDefaults` right after it (Teams below). It is race safe because the settings row is the claim: one transaction inserts it with ON CONFLICT DO NOTHING on the unique `companyId` and only the inserter creates the rest, while a racing request waits on that index and then finds the row.
- Numbers look like OPP-2026-0001 (`formatOpportunityNumber`, the quote number format: prefix, year, a sequence of at least four digits that keeps counting across years). `takeOpportunityNumber` takes the sequence with one atomic increment of `OpportunitySettings.nextNumber` inside the create's transaction, so two creates never share a number and a failed create gives it back. (Quotes, sales orders, and purchase orders use the shared `takeNextNumber`, Record numbers below.)
- Permission keys: `pages.opportunities` (list and open opportunities, read stages, types, and settings), `opportunities.create`, `opportunities.edit` (fields and attachments), `opportunities.delete`, `opportunities.viewTeam` ("View team opportunities": every opportunity in the teams the user is in), `opportunities.viewAll` (everyone's opportunities, any owner, any team), and `settingsSections.opportunities` (stage, type, and settings writes; also reads them). Everyone and new roles start without them; Global Admin has them all.
- Visibility (VOP, `opportunityVisibilityWhere` / `loadViewableOpportunity` / `viewableOpportunityWhere` / `opportunityListWhere` in `src/lib/scoped-loaders.ts`), three levels, all needing `pages.opportunities`: basic, their own opportunities (in any team) plus unassigned ones in teams they belong to; `opportunities.viewTeam`, their own anywhere plus every opportunity in teams they belong to; `opportunities.viewAll` (and Global Admin), every one. Team membership is matched in the same query (the team's members), so joining or leaving a team applies on the next request. Anything else is a 404 on every route (get, patch, delete, timeline, attachments, related); the list, the board, and the sidebar counts filter the same way. Writes after the check use `opportunityWhere`. Quotes, sales orders, and purchase orders keep their own rules; teams change nothing there.
- Owner rule (`mayAssignOpportunityTo(ctx, ownerId, actorInTeam)`): unassigned (null) is always allowed; with `opportunities.viewAll` any member of the opportunity's team; with `opportunities.viewTeam` any member of the team while the user is in it themselves; otherwise only themselves. Anything else is 403 `FORBIDDEN` "You can only assign opportunities to yourself or leave them unassigned", checked before `assertRefs`. The owner must also be an active user of the company (400 "Invalid user") and a member of the opportunity's team (`loadTeamMemberIds`), otherwise 400 "Owner is not in this team" (`OWNER_NOT_IN_TEAM`). Only a PATCH that changes the owner or the team checks membership, so an older opportunity whose owner isn't in its team still saves its other fields. POST leaves the opportunity unassigned unless the body names an owner (see New records below).
- Team rule: `POST /api/opportunities` takes an optional `teamId` (left out, null, or blank is General; `assertRefs` key `teamId`). General is open to every creator; any other team must be one the creator is in, or any team with `opportunities.viewAll` (`mayUseOpportunityTeam`), otherwise 403 "You can only move opportunities to teams you belong to". A PATCH `teamId` follows the same rule (General included: a move needs membership or viewAll), can't be blank (400 "A team is required"), and when the current owner isn't in the new team the same PATCH must name a new owner from it or `ownerId: null`, otherwise 400 "The owner is not in the new team. Choose an owner from that team or leave the opportunity unassigned." The UI clears such an owner itself. A team change records `team_changed`.
- Routes: `GET/POST /api/opportunities` (list: `stageId`, `typeId`, `clientId`, `teamId`, `ownerId` or `unassigned`, `closeFrom`/`closeTo` on the expected close date with the last day included, `q` over title, number, and client name; newest first and unpaged like the quotes list; query ids go through `assertRefs`), `GET/PATCH/DELETE /api/opportunities/[id]`, `GET/POST /api/opportunities/[id]/attachments` and `DELETE .../attachments/[attachmentId]` (mirroring the sales order attachment routes), `GET/POST /api/opportunity-stages`, `PATCH/DELETE /api/opportunity-stages/[id]`, `POST /api/opportunity-stages/reorder` (every stage id in the new order; a list that isn't exactly the company's stages is 409), `GET/POST /api/opportunity-types`, `PATCH/DELETE /api/opportunity-types/[id]`, `POST /api/opportunity-types/reorder` (every type id in the new order, the same rule and 409 as the stage reorder), `GET /api/opportunities/[id]/related` (the Related panel, below), `GET /api/opportunities/sidebar-counts` (the sidebar folder, Teams below), and `GET/PATCH /api/opportunity-settings`. # Quotes and opportunities
- The link: `Quote.opportunityId`, `SalesOrder.opportunityId`, and `PurchaseOrder.opportunityId` (nullable, ON DELETE RESTRICT, no schema change in this branch). A quote's link belongs to its family: every version of a quote (the rows sharing its number) is linked to the same opportunity, `setQuoteFamilyOpportunity` (`src/lib/opportunity-quotes.ts`) writes all of them, and a new version takes its family's link. That keeps one quote one deal, and the value and stage rules read families. The server side lives in `src/lib/opportunity-quotes.ts`; the rules are pure, in `src/lib/opportunity-quote-rules.ts` and `src/lib/opportunity-value.ts`. Every write runs inside the transaction of the change it follows, and deleted opportunities are never touched (every read goes through `opportunityWhere`).
- Linking a quote: an OPEN, not deleted opportunity the user may open (VOP, teams included) whose client and contact are the quote's, through `assertRefs` key `quoteOpportunityId` (needs `clientId` and `contactId` in the same call; a quote without a contact can't link). `POST /api/quotes` and `POST /api/quotes/[id]/copy` take an optional `opportunityId`; `PATCH /api/quotes/[id]` takes `opportunityId` (null or blank unlinks) with `quotes.edit` plus VQ, only while the quote is a DRAFT (the PATCH's own rule). A client or contact change that no longer matches the linked opportunity clears the link (`linkStillMatches`). A copy never takes the original's opportunity. Deleting a linked quote, sales order, or purchase order records the unlink (`deleted: true`). Every link and unlink is a timeline action and an audit entry on the opportunity (`recordRecordLink`), by the user.
- Linking an order: `assertRefs` key `orderOpportunityId`: a not deleted opportunity the user may open, in any stage (the Won prompt opens a sales order for a Won one), of `clientId` when given (the sales order's client, a purchase order's ship to client). `POST` and `PATCH /api/sales-orders` and `/api/purchase-orders` take `opportunityId` (PATCH needs `salesOrders.edit` / `purchaseOrders.edit`). `createSalesOrderFromAcceptedQuote` carries the quote's opportunity (unless it is deleted) and records `sales_order_linked` (by the rep who changed the status, or the system for the portal). A purchase order generated from a sales order takes the sales order's opportunity; a manual one with `salesOrderId` takes the sales order's unless the body names one.
- The picker: `OpportunityPicker` (`src/components/opportunities/`), on the New Quote form, the copy dialog, the quote page (drafts, with `quotes.edit`), the New Sales Order and New Purchase Order forms, and the sales order and purchase order pages (with their edit key), lists `GET /api/opportunities/linkable?for=quote|order&clientId=&contactId=` (`pages.opportunities`; the same rule as the `assertRefs` keys, `loadLinkableOpportunities`), each with number, title, stage, and team, and keeps the current link listed when it no longer is. Hidden without `pages.opportunities`. The forms clear a chosen opportunity when the client or contact changes. `GET /api/contacts/search?id=<contact id>` returns one contact in the search's shape, for a form opened already filled in.
- Panels: `GET /api/quotes/[id]/opportunity` (`pages.quotes` plus VQ), `GET /api/sales-orders/[id]/opportunity` (VSO), and `GET /api/purchase-orders/[id]/opportunity` (VPO) return `{ linked, opportunity, related }` (`loadRecordOpportunityPanel`): the opportunity (number, title, stage, team, owner) only when the user may open it (else `linked: true` alone, "Linked to an opportunity you don't have access to"), and its linked records through `loadOpportunityRelated` (the Related tab's view and cost rules). `RecordOpportunityPanel` shows it on each page, leaving the page's own record out.
- Automatic opportunity: only a quote without one that is sent or accepted gets one (`createsOpportunity`: a move to SENT or VIEWED from any other status, which covers staff send, Mark as sent, send-email, the approval completion that sends, and the status menu choosing Sent or Viewed; or a move to ACCEPTED, from the status menu or the customer portal). A move to DECLINED, EXPIRED, DRAFT, or PENDING_APPROVAL, singly or through the bulk Mark Lost and Mark Expired actions, creates nothing and needs no contact. It is created and the family linked in the same transaction: `prepareQuoteStatusChange` plans it (`planAutoOpportunity`) before the transaction and before any email goes out, so a quote that can't have one is refused with a plain 400 while nothing has changed (no contact: `QUOTE_NEEDS_CONTACT_MESSAGES`, "Add a contact before sending this quote..." or "Add a contact before accepting this quote..."), except a customer's portal acceptance, which is never refused for it: a contactless quote is accepted without an opportunity, and `runQuoteStatusChange` creates it (`createLinkedOpportunity`, which locks the quote row and reads it again so two sends never make two) with `createOpportunityInTransaction` (`src/lib/opportunity-create.ts`, the same create as `createOpportunity` inside the caller's transaction). Its fields: the quote's client and contact, the client's main location, the quote owner's first team by `sortOrder` (else General) with the owner as owner when they are in it and active (else unassigned), the company's quote sent stage (else the first OPEN stage), source QUOTE, the quote's title (else "Quote <number>"), the Valid until date as the expected close date (a stored time becomes its calendar date in `PORTAL_EXPIRY_TIME_ZONE`), no type or value, created by the acting user (the quote owner for the system), and the system note "Created automatically when quote <number> was sent" (or "was accepted"). One created by an acceptance starts at the quote sent stage and the accepted event moves it to the first WON stage. Existing quotes are left alone until they are next sent or accepted.
- Create opportunity: a quote past Draft without one shows "Create opportunity" in its Opportunity panel (`quotes.edit`); `POST /api/quotes/[id]/opportunity` (`quotes.edit` plus VQ; 400 for a draft, 409 when it already has one) creates it the same way with the note "Created from quote <number>" and, in the same transaction, moves it to the stage the quote's status calls for (`buttonStageFor`, `moveToQuoteStatusStage`): ACCEPTED the first WON stage, DECLINED or EXPIRED the first LOST stage, SENT or VIEWED the quote sent stage where it starts. The move goes through `stageChangeData` (closedAt set into WON or LOST) with a `stage_changed` action (its reason names the quote's status, for example "Quote Q-2026-0042 accepted") and a `field_changed` audit entry. The quote's status doesn't change and no quote event is recorded.
- Stage automation, on quote events only (`quoteEventFor`): moving to SENT or VIEWED from anything else is sent, ACCEPTED accepted, DECLINED declined, EXPIRED expired; no change, a move back to DRAFT, SENT to VIEWED, and a request for approval are not events, so a stage moved by hand is only ever moved again by a later quote event. `applyQuoteEvent` records the event (`quote_<event>` timeline action and audit entry) and moves the stage by `stageForQuoteEvent`: sent to the quote sent stage, only from an OPEN stage; accepted to the first WON stage by `sortOrder`, from any stage (LOST included); declined and expired to the first LOST stage, only when no other linked quote is still open or accepted (`otherQuotesState`: another family is open when one of its rows is a draft or its current version, the active one, is SENT or VIEWED, and accepted when any row was accepted; in the quote's own family only a draft counts, since older versions stay SENT after a newer one goes out). An accepted quote keeping a decline elsewhere from moving the deal to Lost is a decision of this branch. The move goes through `stageChangeData` (stageChangedAt, closedAt) as one conditional write on the stage it was read in (a move made meanwhile is kept), with a `stage_changed` action holding the reason ("Quote Q-2026-0042 accepted") and a `field_changed` `stageId` audit entry. The actor is the user whose action it was, or the system (no author, "System") for the customer portal and expiry.
- Where the automation runs, always inside the transaction that changes the quote: `POST /api/quotes/[id]/send` (Mark as sent), `POST /api/quotes/[id]/send-email` (planned before the email is sent; a failure after Microsoft accepted it answers 500 "The email was sent, but the quote couldn't be marked sent. Mark it as sent from the status menu."), `POST /api/quotes/[id]/status` (every status, and the bulk Mark Lost and Mark Expired actions through it), `completeApprovedQuote` (`src/lib/quote-approval.ts`, by the approver; a quote that can't have its opportunity is not sent and keeps its held email like a failed send), the portal accept (`prepareQuoteStatusChange` before, `runQuoteStatusChange` in the transaction that holds the conditional decision) and decline (`applyQuoteEvent` in that transaction), the portal GET that records an expired quote as EXPIRED, and `createSalesOrderFromAcceptedQuote` (the link it carries). Any new code that changes a quote's status calls `prepareQuoteStatusChange` and `runQuoteStatusChange` the same way.
- Expiry: a quote's status becomes EXPIRED only when it is stored: by the status route (and the bulk Mark Expired action), by the portal GET the first time the customer opens a link after its Valid until date while it was SENT or VIEWED, or by the daily quote expiry job (Quote expiry job below). Between job runs a quote only past its date stays SENT (its portal answers 410 either way, worked out from `isPastExpiry`). The expired rule runs on every stored path.

# Quote expiry job
- `expireOverdueQuotes({ now, companyIds, limit, dryRun })` (`src/lib/quote-expiry-job.ts`) stores EXPIRED for every quote that is SENT or VIEWED (`AWAITING_RESPONSE_STATUSES`) and past its Valid until date by the portal's rule (`isPastExpiry`), oldest date first, at most `limit` (default `EXPIRE_QUOTES_DEFAULT_LIMIT`, 200) per run. Only the current version of each family: a superseded version (`isSupersededVersion`, the portal's rule) is skipped, since its customer can't act on it and its expired event could move the opportunity to Lost while the newer version is still open. `companyIds` limits it (an empty list does nothing); `dryRun` lists the quotes without changing anything.
- Each quote is expired in its own transaction through the staff status change path: `prepareQuoteStatusChange`, then the row locked (`FOR UPDATE`) and read again (still SENT or VIEWED and past its date, otherwise skipped), the terms freeze, the status write, and `runQuoteStatusChange` with `actorId: null`, so `applyQuoteEvent` records the expired event and moves the opportunity (the declined and expired rule) by System on the timeline and in the audit log. Running it twice expires nothing new. A failing quote is collected (`errors`, as `errorSummary`) and the rest carry on. It answers `checked`, `expired`, `skipped`, `errors`, `limitReached`, and `items` (ids, numbers, dates, opportunity ids; never shown by the route).
- `GET /api/cron/expire-quotes` runs it. It is public in `check-route-access.ts` and protected by `CRON_SECRET`: unset, 503 "Not configured" and nothing runs; the request must carry `Authorization: Bearer <CRON_SECRET>` (compared in constant time as sha256 digests), otherwise 401 "Unauthorized" with no details. It answers only `{ checked, expired, skipped, errors, limitReached }` and logs one line with those counts (and the first failures by quote id and error kind), never tokens or customer data. `maxDuration` 60.
- `vercel.json` holds the two cron entries: `/api/cron/expire-quotes` at `0 6 * * *` (06:00 UTC, early morning US Eastern) and `/api/cron/close-resolved-tickets` at `15 6 * * *` (Tickets below). Both check the secret with `cronRefusal` (`src/lib/cron-auth.ts`). Vercel runs crons only on the production deployment (never previews or local dev), and sends the bearer token itself once `CRON_SECRET` is set in the project's environment variables. Without it set the route answers 503 every day and nothing expires.
- `scripts/dev-only/run-quote-expiry.ts` runs it by hand on the dev database (the dev-only guard, `--yes`): a dry run by default listing each quote that would expire (number and version, company, Valid until, linked opportunity number), `--apply` to expire them, `--company <id>` and `--limit <n>` to narrow it. Exit 0 done, 1 refused, 2 a quote failed. Claude Code never runs it.
- Value: while an opportunity has linked quotes its value is the sell total of its latest linked quote (`latestQuoteValue` in `src/lib/opportunity-value.ts`): the most recently sent family's current version (the active one, else its most recently sent) when any linked quote was sent, otherwise the most recently updated linked draft. The total is the quotes list's price total (`quoteSellTotal`, never cost or margin) rounded to cents in one place (`moneyText`). It is worked out on read, never stored: `withQuoteValues` / `withQuoteValue` add `quoteValue` (`{ quoteId, label, value }`, or null without linked quotes) to the opportunity list, detail, PATCH, POST, and restore responses, and every screen shows `opportunityDisplayValue` (the board cards and column totals, the list's Value column and sort, the opportunity page). Every linked quote counts, whether or not the viewer may open it, like the manual value. While quotes are linked the panel's Expected value is read only with "From quote <number>" (a link for users with `pages.quotes`), and the PATCH refuses `expectedValue` with 400 `VALUE_FROM_QUOTE`. Without linked quotes it stays the manual `expectedValue`.
- Client change rule: while any quote, sales order, or purchase order is linked, `planOpportunityUpdate` refuses a new client with 409 `CLIENT_LOCKED` "Unlink this opportunity's quotes and orders before changing its client" (`CLIENT_LOCKED_MESSAGE`, `hasLinkedRecords`), so the PATCH, the inline panel, and the audit log's undo (which sends the old client through the planner and answers its 409 with the same reason) all follow it. A new contact of the same client is allowed, and a request naming the current client is not a change. The panel's Client field shows the reason under it instead of opening its editor, and the contact editor keeps to the current client.
- Won with no quote: when a user moves an opportunity into a WON stage (the panel, a Won button or note, a board drag) and it has no linked quote, the page asks "Create a sales order for this opportunity?" (`offersSalesOrderAfterMove`, `WON_SALES_ORDER_PROMPT`) with Create (the New Sales Order form filled in) and Not now, only for users with `pages.salesOrders` and `salesOrders.create`. Never automatic, and never for a move within WON.

# Record numbers
- Quote, sales order, and purchase order numbers come from one shared counter: `NumberSequence` (`prisma/schema.prisma`: `companyId`, `key`, `nextValue`, timestamps, unique on (`companyId`, `key`)), one row per company and record type, with the keys in `NumberSequenceKey` (`src/lib/record-number.ts`: `quote`, `salesOrder`, `purchaseOrder`, `ticket`). Opportunities keep their own counter (`takeOpportunityNumber`, above).
- `takeNextNumber(tx, companyId, key)` returns the next sequence and moves the counter on, always inside the transaction that creates the record, so a failed create gives the number back. It is one atomic increment of the counter row (locked until the transaction ends). When the company has no counter for the key yet it locks the company's row (`SELECT ... FOR NO KEY UPDATE`, like `ensureTeamDefaults`), looks again, and only then creates the counter, starting after the highest sequence any of the company's stored numbers holds for that key (`firstSequence`, parsing the trailing `-YYYY-N` of every number whatever its prefix or year) and never below the old row count plus one, so numbering carries on seamlessly. `takeRecordNumber(tx, companyId, key, prefix)` formats it with `formatRecordNumber`: prefix, the current year, and the sequence padded to four digits (Q-2026-0001, SO-2026-0042, PO-2026-12345), exactly the format used before. The sequence keeps counting across years (one key per type, no yearly restart), and a deleted record's number is never handed out again.
- Every new numbered record must take its number with `takeNextNumber` (add its key to `NumberSequenceKey` and its existing numbers to `EXISTING` there), never by counting rows. Today's callers: `POST /api/quotes`, `POST /api/quotes/[id]/copy`, `POST /api/sales-orders`, `createSalesOrderFromAcceptedQuote` (`src/lib/sales-orders.ts`), `POST /api/purchase-orders` (manual and generated from sales order lines), and `createTicket` (`src/lib/ticket-create.ts`, deleted tickets' numbers included in `EXISTING`). A new version keeps its family's number and takes the next version.
- Unique constraints make duplicates impossible: `Quote` (`companyId`, `quoteNumber`, `version`), since every version is its own row sharing the family's number, `SalesOrder` (`companyId`, `soNumber`), and `PurchaseOrder` (`companyId`, `poNumber`). A create that still collides (`isNumberCollision`, a P2002, for example a row written by an instance still on the old numbering during a deploy) answers 409 `{ error: "That number is already in use. Please try again.", code: "NUMBER_TAKEN" }` (`NUMBER_TAKEN_MESSAGE`); a new version that loses a race for its version number answers 409 "Another version of this quote was just created. Please try again."; `createSalesOrderFromAcceptedQuote` returns the sales order another request already created for the quote. Any other failure is `userFacingError`.
- Before deploying the migration that adds those constraints, run `scripts/dev-only/report-duplicate-numbers.ts` (read only; sources in `scripts/dev-only/lib/duplicate-numbers.ts`) against the live database: it prints the database name and host, then every company and number held by more than one row for each constraint, with the record ids, created dates, and labels, and ends with "No duplicates found." or the count. Each duplicate must be renumbered by hand first, or the migration fails. It follows the dev-only guard by default (`npx tsx scripts/dev-only/report-duplicate-numbers.ts --yes`) and reads the live database only like `report-file-links.ts`: `DB_NAME` exactly `psasync`, both `--yes` and `--allow-live-read-only`, no env file loaded, and the database name typed exactly. Its client is wrapped by `readOnlyClient`. Exit 0 report printed, 1 refused or not confirmed, 2 failed.

# Teams
- Admin managed groups of users, shared by opportunities and tickets (a ticket's team is its queue, Tickets above) (`prisma/schema.prisma`): `Team` (company, `name` unique per company, `description`, `isDefault`, `sortOrder`, `roundRobinEnabled`, `roundRobinLastUserId`), `TeamMember` (team and user, unique pair, cascading with either), and `TeamDefaultRole` (team and role, unique pair, cascading with either). A user can be in several teams. The ticket queues Helpdesk, Alerts, and Lv2 Escalation are ordinary teams made by `ensureTicketDefaults`.
- General: every company has exactly one default team (`isDefault`), named General when it is created. `ensureTeamDefaults(companyId)` (`src/lib/team-defaults.ts`) creates it on first use (every team and opportunity route and the sidebar counts call it; never company creation or a migration) and, in the same transaction, puts every opportunity of the company without a team into it. It is race safe because the transaction first locks the company's row (`SELECT ... FOR NO KEY UPDATE`), so two requests run one after the other and the second finds the team; once General exists and no opportunity lacks a team it is two small reads. General can be renamed but never deleted, and nobody is added to it automatically. `createOpportunity` puts a new opportunity in the given team, or General.
- Effective roles: a user's roles are their directly given roles plus the default roles of every team they are in (`effectiveRoles` and `rankOf` in `src/lib/team-roles.ts`), worked out by `getEffectiveAccess` on every request and never copied into `UserRole`, so joining or leaving a team, or changing a team's default roles, applies on the user's next request with nothing to keep in sync. Every permission check, `access.rank` (approval workflows, the Roles and Manage Users rank rules), Manage Users' hierarchy check on the target user (PATCH users/[id]), and role based sales order notifications use them. `EffectiveAccess.roleIds` holds the effective role ids and `teamIds` the user's teams. Only the user's own company's teams count, and Everyone and Global Admin never come from a team.
- Grant rule (`roleGrantRefusal` / `roleGrantProblem` in `src/lib/role-grants.ts`, the one helper every grant uses, client safe): a role may be given to a user directly (invite, PATCH users/[id] `roleIds`) or through a team (a team default role, or adding a member to a team that has it) only when the acting user ranks above it (`assignsRoleAtOrAboveRank`) AND holds, through their own effective roles, every permission it grants (`findPermissionEscalations`, the Roles screen rule, on the role's stored permissions with legacy keys dropped; a higher `maxDiscount` counts). Otherwise 403 `FORBIDDEN`: a rank refusal keeps its existing message, a permission refusal names the role ("You can't give the NAME role because it includes permissions you don't have", or for adding a member "You can't add members to this team because its NAME role includes permissions you don't have"). Used by POST /api/users, PATCH /api/users/[id] (`roleIds` and `teamIds`), POST /api/teams, PUT /api/teams/[id]/default-roles (`checkDefaultRoles`), and PUT /api/teams/[id]/members (`teamsGrantRefusal`, reading the team's roles inside the write's transaction). Global Admin and Everyone can never be default roles (400). Removing a role, a default role, or a member is never restricted by it. For the screens, `GET /api/roles` returns each role's `grantRefusal` and `GET /api/teams` each team's `memberGrantRefusal` (to `settingsSections.teams`), so role permissions never reach the browser.
- Membership rank rule (`membershipChangeRefusal` in `src/lib/team-roles.ts`, applied by `membershipChangesRefusal` in `src/lib/teams.ts` and PATCH users/[id] `teamIds`): every user added to or removed from a team (PUT members, POST /api/teams `memberIds`, Manage Users' Edit Teams) must rank below the acting user by effective rank (`loadEffectiveRanks`, the Manage Users hierarchy rule), otherwise 403 "You can only add or remove team members ranked below you". Anyone may remove themselves; adding themselves follows the rule. Global Admin passes. `GET /api/users` returns each user's `teamChangeRefusal` to `settingsSections.teams` holders.
- Permissions: `settingsSections.teams` manages teams (Settings > Teams and every Teams write); changing a user's teams in Manage Users needs it on top of `settingsSections.users`. `opportunities.viewTeam` is the middle visibility level (Opportunities above). Global Admin sees the Teams section, the sidebar folder, the Team field, and team markers in Manage Users, and still sees every opportunity.
- API (every route `requireAccess`, company scoped, `ensureTeamDefaults` first; `toTeamResponse` in `src/lib/teams.ts` is the one team shape: `id`, `name`, `description`, `isDefault`, `sortOrder`, `memberCount`, `defaultRoles` (id, name, rank, color, isGlobalAdmin), `isMember` (the caller), `assignableOwnerIds` (the active members the caller may make an opportunity's owner there, `visibleTeamMemberIds`; empty without `pages.opportunities`), and `members` (id, name, active) only with `settingsSections.teams`): `GET /api/teams` (in `sortOrder`), `POST /api/teams` (`name`, `description`, optional `memberIds` and `defaultRoleIds` under the same rules; the new team goes last), `PATCH /api/teams/[id]` (`name`, `description`; a name another team has, ignoring case, is 400), `DELETE /api/teams/[id]` (General 409 `DEFAULT_TEAM`; a team any opportunity is in, deleted ones included, 409 `TEAM_IN_USE` "This team has N opportunities..." plus how many are deleted; answers `{ deleted: true }`), `POST /api/teams/reorder` (`teamIds`, every team id in the new order; a list that isn't exactly the company's teams is 409 `TEAM_LIST_CHANGED`; answers the list), `PUT /api/teams/[id]/members` (`userIds` replaces the members: every id a user of the company, every added one active), and `PUT /api/teams/[id]/default-roles` (`roleIds` replaces the default roles). Ids from the URL go through `loadTeam` / `teamWhere`; body ids through `assertRefs` (`userId`, `companyUserId`, `roleId`, `teamId`). `PATCH /api/users/[id]` takes `teamIds` (replaces the user's teams) with the grant rule.
- Settings > Teams (`TeamsSettingsPanel`, listed with `settingsSections.teams` through `PANEL_PERMISSION`): the teams in order, dragged to reorder (the Opportunity Settings panel's dnd-kit helpers, with `DndContext` around the list), each with its member count, its default roles as role pills, and General marked Default without Delete. Create and edit in a dialog (name, description, members, default roles; members and roles are `SearchableChecklist`s, members in the shared user picker order), where roles the user couldn't give are disabled with the reason (`defaultRoleBlockReason`, from `grantRefusal`), adding members to a team giving such a role is disabled (`addMemberBlockReason`), and users the user can't add or remove are disabled with the reason (`memberChangeBlockReason`, from `teamChangeRefusal`; unticking themselves always works). Saving an existing team sends only what changed, default roles before members. Delete asks first; a 409 shows as is.
- Manage Users: role pills show team granted roles (`teamRoles`) with a team icon and the tooltip "From team NAME" (a role also given directly shows once, marked "Given directly and from team NAME"), in the same top two plus "+N more" layout. A role only a team gives is ticked and disabled in the role checklist, with the tooltip saying to remove the user from the team instead. Role choices the user couldn't give the person are disabled with the grant rule's reason (a role already held directly can still be removed). With `settingsSections.teams` the row menu has Edit Teams (a checklist of teams; a team whose default roles fail the grant rule can't be added, and a user ranked at or above the editor can't be added to or removed from any team, though the editor may take themselves out of one).
- Sidebar folder (`OpportunitiesFolder` in `src/components/layout/`, gated by `pages.opportunities`): the Opportunities entry links to the board and its chevron opens a folder (open or closed remembered per browser in localStorage, every read and write in try/catch) with All opportunities, then each team in `sortOrder` (every team with `opportunities.viewAll`, otherwise the user's own teams), each expanding to Unassigned and its members (`visibleTeamMemberIds`: all members with viewAll, or with viewTeam in their own teams; only the user themselves otherwise), sorted with the shared user picker helper. Every row shows its count of OPEN opportunities (stage category OPEN) the user can see, from one request, `GET /api/opportunities/sidebar-counts` (`pages.opportunities`; `{ total, teams: [{ id, name, isDefault, count, unassigned, members: [{ id, name, count }] }] }`, built by `sidebarCounts` from the teams and one grouped count over `opportunityListWhere`). A team opens `?team=<id>`, a member `?team=<id>&owner=<user id>`, Unassigned `?team=<id>&owner=unassigned`. Counts reload when the folder opens, when the window regains focus, and on `notifyOpportunitiesChanged()` (the `psasync:opportunities-changed` window event), which the Opportunities pages send after a create, a stage move, an owner or team change, a note that moves the stage, and a delete. The mobile menu shows the same folder; the sidebar has no collapsed mode.

# Timeline
- `TimelineEntry` (`prisma/schema.prisma`) is a record's activity history, shared by opportunities and tickets (each entry has exactly one of `opportunityId` and `ticketId`, both nullable and cascading; `TimelineSubject` in `src/lib/timeline.ts`), with the same model, route pattern (`src/app/api/opportunities/[id]/timeline` and `.../timeline/[entryId]`), helpers (`src/lib/timeline.ts`, server side; `src/lib/timeline-actions.ts`, client safe), and component (`Timeline` in `src/components/timeline/`, which takes the record's timeline URL). Fields: `companyId`, `opportunityId` (nullable, ON DELETE CASCADE), `kind` (`TimelineEntryKind`: NOTE, ACTION, EMAIL_OUT (an email sent with the Email action), and EMAIL_IN, unused until incoming replies arrive in a later phase), `authorId` (nullable, ON DELETE SET NULL; null is the system), `body` (NOTE rich text HTML), `action` and `data` (ACTION key and its before and after values, names stored next to ids so an entry reads correctly after a rename or delete), `editedAt`, `createdAt`. Indexes on `companyId`, (`opportunityId`, `createdAt`), and (`ticketId`, `createdAt`). Tickets add the action keys `status_changed` (with an optional `reason`), `priority_changed`, and `assignee_changed` (`reason` "Round robin" for a round robin assignment), and `created` carries `status` for a ticket where an opportunity's carries `stage`.
- ACTION entries are written with `recordTimelineActions` inside the same transaction as the change, by the user who made it. Keys (`TIMELINE_ACTIONS`, read as sentences by `describeTimelineAction`): `created`, `stage_changed`, `team_changed` (team names and ids), `owner_changed`, `type_changed`, `client_changed`, `contact_changed`, `title_changed`, `expected_value_changed`, `expected_close_date_changed`, `attachment_added`, `attachment_removed`, `restored` (a deleted record restored from the audit log), and for links and quote events (Quotes and opportunities below) `quote_linked`, `quote_unlinked`, `quote_sent`, `quote_accepted`, `quote_declined`, `quote_expired`, `sales_order_linked`, `sales_order_unlinked`, `purchase_order_linked`, `purchase_order_unlinked` (data `{ record: { id, name } }`, the name the record's number, and `deleted: true` when the link went because the record was deleted). A `stage_changed` made by a quote event also stores `reason` ("Quote Q-2026-0042 accepted"), read in brackets after the move. For opportunities `opportunityChangeActions` (`src/lib/opportunity-timeline.ts`) compares the opportunity read inside the PATCH's transaction with the saved one and records one entry per field that changed, nothing for a PATCH that changes nothing. A stage's category change (the closedAt update) records nothing, since no opportunity's stage changed. `POST /api/opportunities` records `created` and then, a millisecond later in the same transaction, the optional `initialNote` as the first NOTE.
- Routes: `GET .../timeline` (`pages.opportunities` plus VOP) returns `{ entries, nextCursor }`, newest first (`createdAt`, then `id`), `TIMELINE_PAGE_SIZE` (25) at a time; `?cursor=` must be an entry of the same opportunity (`loadOpportunityTimelineEntry` in `src/lib/scoped-loaders.ts`), otherwise 400 "Invalid cursor". `POST .../timeline` (`opportunities.edit` plus VOP) adds a note by the caller. `PATCH` and `DELETE .../timeline/[entryId]` (`opportunities.edit` plus VOP; an entry of another opportunity or company is a 404) only touch NOTE entries, and only the note's own author, Global Admin included: anything else is 403 `FORBIDDEN` ("Only notes can be edited or deleted" or "You can only edit or delete your own notes"). Editing sets `editedAt`. ACTION and EMAIL entries can never be edited or deleted.
- A note can change its record's stage: `POST .../timeline` takes an optional `stageId` (a string, checked with `assertRefs` key `opportunityStageId`, otherwise 400 "Invalid stage"; the same `opportunities.edit` as the note). In one transaction it moves the opportunity with `stageChangeData` (the PATCH's rule: `stageChangedAt`, `closedAt` set into WON or LOST and cleared into OPEN) and writes ONE entry, the NOTE, with the move in its data as `{ stageChange: { from, to } }` (id, name, and category; read with `noteStageChange` in `src/lib/timeline-actions.ts`), never a separate `stage_changed` entry. A `stageId` equal to the current stage moves nothing and stores no move. Editing the note later changes only its text. The note card shows the move as a tinted pill, for example "New to Qualified".
- Action button bar: `ActionButtonBar` (`src/components/timeline/ActionButtonBar.tsx`) renders the company's buttons (Action buttons below) as rounded pills filled with each button's color, the text white or near black for contrast (`buttonTextColor`), from plain, serializable definitions (`ActionButtonDefinition` in `src/lib/timeline-buttons.ts`, made from a stored button by `toActionButtonDefinition`): `{ id, label, icon, color, opens }`, where `icon` is a name from `ACTION_BUTTON_ICONS`, `color` a `#RRGGBB` hex, and `opens` is `{ kind: "note" | "email" | "quote", stageMode, stage?: { id?, category? }, noteRequired }` (`presetStageId` picks a FIXED button's stage). The bar wraps onto more lines without shrinking buttons. `unavailableReason` dims a button, keeps it focusable, shows the reason as its tooltip, and makes it do nothing. On the opportunity page the bar sits in the header and opens the composer through the timeline's handle (`ref` with `openComposer`, `showButtons={false}`, `onComposerChange` for the pressed button; the composer scrolls into view). A NOTE button opens the composer inline at the top of the timeline (its label, the note editor, the stage as the button allows: nothing for NONE, a "Change stage to" select grouped Open, Won, Lost with "No change" first for CHOOSE, the fixed stage shown read only for FIXED; Post, disabled until there is text when the note is required, and until the stage moves when it is optional and empty; and Cancel, which asks before discarding typed text); switching buttons keeps the text and changes only the preset stage. The note is sent with `actionButtonId`, so the server applies the same rules. `Timeline` takes `buttons`, `unavailableReason`, optional `stages`, `email` (the Email action's context), and `onPosted` (the opportunity page reloads after a note or email that moved the stage).
- A note may name the button it was posted with: `POST .../timeline` takes an optional `actionButtonId` (`assertRefs` key `actionButtonId`; `readActionRequest` in `src/lib/action-buttons.ts`). It must be a NOTE button the opportunity shows (not hidden, set for opportunities, an available kind), otherwise 400 "Invalid action button". Its stage rule (`buttonStageRule`) decides the stage: NONE refuses a `stageId` (400 "This action doesn't change the stage"), CHOOSE takes the one sent, FIXED uses its own and refuses a different one (400 "This action always moves to its own stage"). Its note rule decides the text: REQUIRED as before, OPTIONAL lets the body be empty (stored as null) as long as the stage moves, otherwise 400 "A note can't be empty". The entry stores the button as `data.actionButton` (`{ id, label }`, read with `entryActionButton`), shown as a small label on the card. A note without `actionButtonId` follows the old rules (text required, any company stage).
- Note bodies go through the quote terms sanitizer: `readNoteBody` on save (refusing a non string, more than `TIMELINE_NOTE_MAX` characters, or a note with no text after sanitizing, 400 "A note can't be empty") and `toTimelineEntryResponse` on the way out. Authors are returned as id and name only.

# Action buttons
- `ActionButton` (`prisma/schema.prisma`) is a company's configurable button above a record's timeline (the HaloPSA style "actions"), shared by opportunities and tickets: `label` (at most 40 characters), `icon` (a name from `ACTION_BUTTON_ICONS` in `src/lib/timeline-buttons.ts`), `color` (`#RRGGBB`, stored upper case), `forOpportunities` and `forTickets` (at least one), `kind` (`ActionButtonKind`: NOTE, EMAIL, RAISE_QUOTE, APPOINTMENT, CHILD_TICKET), `stageMode` (`ActionStageMode`: NONE, CHOOSE, FIXED), `fixedStageId` (an `OpportunityStage`, ON DELETE RESTRICT, required for a FIXED button that shows on opportunities), `fixedTicketStatusId` (a `TicketStatus`, ON DELETE RESTRICT, the status a FIXED button moves a ticket to; a FIXED button that shows on tickets without one is left off tickets), `noteMode` (`ActionNoteMode`: OPTIONAL, REQUIRED), `isHidden`, and `sortOrder`. Only NOTE and EMAIL buttons may have stage settings. `checkActionButton` leaves `fixedTicketStatusId` out when the input doesn't hold it (the Settings dialog doesn't send it yet, so its saves keep the stored one) and drops it when the button isn't FIXED; the routes refuse a request that names one for a button that isn't FIXED (400) and check it with `assertRefs` (`ticketStatusId`). The rules are `checkActionButton` in `src/lib/action-button-rules.ts` (client safe, shared with the Settings dialog), which checks the whole button (a PATCH is laid over the stored button with `mergeButtonPatch` first); `fixedStageId` goes through `assertRefs` (`opportunityStageId`).
- Defaults are lazy: `ensureActionButtonDefaults(companyId)` (`src/lib/action-buttons.ts`) creates Note (NOTE, CHOOSE, required, the brand primary color, opportunities and tickets), Email (EMAIL, NONE, required, the brand accent, opportunities and tickets), Raise Quote (RAISE_QUOTE, NONE, optional, the brand primary color, opportunities and tickets), Won (NOTE, FIXED to the first WON stage by `sortOrder`, optional, success green `#3A9742`), and Lost (NOTE, FIXED to the first LOST stage, required, danger red `#E62B34`), in that order, the first time any action button route (or a note or email naming a button) runs for the company; never at company creation or by a migration. It is race safe like `ensureTeamDefaults` (the transaction locks the company's row, `SELECT ... FOR NO KEY UPDATE`, and checks again). The company's last button can't be deleted (409 `LAST_BUTTON`, hide it instead), so the defaults never come back.
- Available kinds: `AVAILABLE_ACTION_KINDS` in `src/lib/timeline-buttons.ts` (NOTE, EMAIL, and RAISE_QUOTE today) is the one list of kinds whose feature exists. Every kind can be configured in Settings, but only available kinds show on records. A later branch turns a kind on by building its feature, adding the kind to that list, and handling its `opens` in `toActionButtonDefinition` and the page (the `Timeline` composer for kinds that write an entry). A Raise Quote button opens `{ kind: "quote" }` (no stage, no text): the opportunity page sends the user to `raiseQuoteHref` (the quotes page with `?raiseFor=<id>`, which opens the template picker, whose templates go to the New Quote form with `?opportunity=<id>`), and the form starts on the opportunity's contact (and client) with the link. Companies whose buttons already existed don't get it: an admin adds one in Settings > Action Buttons (New button, kind Raise quote, Shows on Opportunities, any icon and color).
- Visibility: everyone who can open a record sees all of its buttons (not hidden, set for that record type, an available kind, in `sortOrder`). Using one needs the record's edit permission (`opportunities.edit`, or `tickets.edit` on a ticket): without it every button is dimmed with the tooltip "You need edit access to use this". Raise Quote is also dimmed without `pages.quotes` and `quotes.create`, and on an opportunity that isn't in an OPEN stage (a quote only links to an open one). An Email button is also dimmed, with how to connect a mailbox, when the user has no mailbox they can send from (`emailUnavailableReason`).
- Routes: `GET /api/action-buttons?for=opportunity` (`pages.opportunities` or `settingsSections.actionButtons`) returns the record's buttons as `ActionButtonDefinition`s; any other `for` is 400 "Invalid record type". Without `for` it is the admin list (every button, hidden ones and unavailable kinds included, each with `available`, and its `fixedStage`), which needs `settingsSections.actionButtons`, like `POST /api/action-buttons` (goes last), `PATCH` and `DELETE /api/action-buttons/[id]` (another company's is a 404), and `POST /api/action-buttons/reorder` (`buttonIds`, every id in the new order; a list that isn't exactly the company's buttons is 409 `BUTTON_LIST_CHANGED`). Deletes and reorders run in `withActionButtonsLock` (the company row lock; a refusal rolls back). A stage a button moves to can't be deleted: the stage DELETE answers 409 `STAGE_USED_BY_BUTTON` naming the button. `GET /api/opportunity-stages` also takes `settingsSections.actionButtons` (the dialog's fixed stage list).
- Permission: `settingsSections.actionButtons` ("Action Buttons") manages them; Settings > Action Buttons (`ActionButtonsSettingsPanel`, listed through `PANEL_PERMISSION` under Opportunities) shows the buttons in order, dragged to reorder (the Opportunity Settings dnd-kit helpers, `DndContext` around the list), each with a live preview (`ActionButtonPill`), where it shows, its kind, its stage and text rules, Hidden, and "Coming later" for an unavailable kind. Create and edit in a dialog: label, an icon grid, a color palette (the brand primary and accent from `GET /api/company-settings` plus fixed colors) with a custom hex field, a live preview and a contrast badge that warns below 4.5:1 (`buttonContrastWarning`), shows on, kind, stage mode and fixed stage (NOTE and EMAIL only), text required or optional, and hidden. Delete asks first; 400 and 409 messages show as they are.

# Email action
- An EMAIL button opens an email composer in the same place as the note composer, with the same discard warning: From (the Send Quote rule with the sender as the owner, `resolveOwnSender` / `ownSenderOptions` in `src/lib/quote-sender.ts`: the shared mailbox when Quote Settings names one, otherwise the user's own, and a picker of the company's mailboxes only with `quotes.sendAsOthers`), To (the opportunity's contact to start, more from the client's contacts by name or email, or typed addresses, as removable chips), CC and BCC (collapsed until "Add CC or BCC"), Subject (`defaultEmailSubject`: "[OPP-2026-0001] Title"), the rich text message, the company signature (`CompanySettings.emailSignature`, plain text from Settings > Notifications) shown as "Added under your message", the opportunity's attachments as tick boxes with their total against `EMAIL_ATTACHMENTS_MAX_BYTES` (3 MB, Graph's limit for one sendMail body once base64 grows it), and the stage per the button. Send Quote itself attaches only its generated PDF and adds no signature; this is the first email to use either.
- `GET /api/opportunities/[id]/email-options` (`opportunities.edit` plus VOP) returns the From choices (the same shape as the quote `send-options`, both built by `senderOptionsFor`), `signature`, `maxAttachmentBytes`, and the client's contacts that have an email address (id, name, email). Never tokens.
- `POST /api/opportunities/[id]/email` (`opportunities.edit` plus VOP): `to`, `cc`, `bcc` (lists of addresses or comma separated text, each checked with `isEmailAddress` in `src/lib/email-address.ts`, at least one To, at most 20 in all, `readEmailRecipients` in `src/lib/record-email.ts`), `subject` (every line break and control character becomes a space, `cleanEmailSubject`; required, at most 255), `body` (sanitized like a note; required unless the button's note is optional; empty answers "A message is required"), `attachmentIds` (at most 20, `assertRefs` key `opportunityAttachmentId` tied to `opportunityId`, so another opportunity's is 400 "Invalid attachment"; their total over 3 MB is a 400), `actionButtonId` (an EMAIL button, the same `readActionRequest` rules as a note), `stageId`, and `sendAsConnectionId`. Then each user may send 30 emails per 10 minutes (`record-email` in `SUBJECT_LIMITS`, keyed by user id; a refused request isn't counted; 429 "You've sent a lot of emails in a short time..."), the files are read with `readStoredObject`, and the email goes out through `sendFromMailbox` (`src/lib/microsoft-mail.ts`, the token refresh and Graph sendMail that Send Quote and the notification emails also use). Only after Microsoft accepts it does one transaction write an EMAIL_OUT entry (author, `data.email` with from, to, cc, bcc, subject, and attachment ids and names, the sent HTML as `body`, `data.actionButton`) and apply the stage change on the same entry (`data.stageChange`, `stageChangeData`), like a note. A failed send records nothing and answers its plain error; a failure to record after a successful send answers 500 "The email was sent, but it couldn't be added to the timeline."
- The timeline shows an EMAIL_OUT entry as an "Email sent" card: from, to, CC, BCC, subject, and files (`emailOutDetails`), and the body collapsed to a few lines with Show more when it is long. Email entries can never be edited or deleted.
- Incoming replies (EMAIL_IN) come in a later phase.

# Audit log
- `AuditLogEntry` (`prisma/schema.prisma`) is the admin record of every change, shared by every record type and kept forever (nothing deletes entries): `companyId`, `recordType` (`AuditRecordType`: OPPORTUNITY and TICKET now; QUOTE, SALES_ORDER, and PURCHASE_ORDER for later branches), `recordId` (a plain string with no relation, so entries outlive their records), `recordLabel` (a snapshot, for example "OPP-2026-0007 New laptops"), `action`, `field` (the PATCH body key, for example `ownerId`), `before` and `after` (Json, names stored next to ids), `actorId` (ON DELETE SET NULL) and `actorName` (a snapshot; "System" for none), `undoneAt` and `undoneById` (ON DELETE SET NULL), `undoOfId` (on an undone entry, the entry it reverses), `createdAt`. Indexes on (`companyId`, `createdAt`) and (`companyId`, `recordType`, `recordId`, `createdAt`).
- Every record type must record its changes. Entries are written with `recordAudit(tx, { companyId, actorId, entries, at? })` (`src/lib/audit-log.ts`) inside the same transaction as the change they describe, never after it; it reads the actor's name in that transaction and writes nothing for an empty list. A change that changes nothing records nothing. Values follow `src/lib/audit-values.ts` (client safe): refs as `{ id, name }`, text, decimal text, YYYY-MM-DD dates, notes as `{ entryId, text }` (plain text), attachments as `{ id, fileName, fileSize }`, emails as `{ entryId, to, subject }`. Action keys and their plain words are `AUDIT_ACTIONS` / `AUDIT_ACTION_LABELS`, fields `AUDIT_FIELD_LABELS`; a new key goes there first.
- Opportunities record (builders in `src/lib/opportunity-audit.ts`): `created` (`createOpportunity`), one `field_changed` per changed field from the same comparison the timeline uses (`opportunityFieldAudits` over `opportunityChangeActions`: title, client, contact, location, team, owner, stage, type, expected value, expected close date), stage moves by notes, action buttons, and emails (`field_changed` `stageId`), `closed_date_changed` (closedAt following its stage's category change, for every opportunity whose closedAt changed, deleted ones included), `deleted`, `restored`, `note_added`, `note_edited` (text before and after; nothing when the text is the same), `note_deleted` (the deleted text), `attachment_added` and `attachment_removed` (name and size), `email_sent` (to and subject), `undone`, and the link and quote event entries (`quote_linked`, `quote_unlinked`, `quote_sent`, `quote_accepted`, `quote_declined`, `quote_expired`, `sales_order_linked`, `sales_order_unlinked`, `purchase_order_linked`, `purchase_order_unlinked`, the record as `{ id, name }` in after, or before for an unlink, `opportunityRecordAudit`). A stage moved by a quote event is a `field_changed` `stageId`, like any move, so it can be undone. Deleted notes and attachments are not restorable; the log keeps what was removed.
- Soft delete: `DELETE /api/opportunities/[id]` keeps its permission and its linked records 409 (checked again inside the transaction) and sets `deletedAt` and `deletedById` with a `deleted` entry in one transaction. The one "not deleted" condition is `NOT_DELETED_OPPORTUNITY` in `src/lib/scoped-loaders.ts`, built into `opportunityWhere`, `viewableOpportunityWhere`, `opportunityListWhere`, `opportunityAttachmentWhere`, `opportunityAttachmentsWhere`, `opportunityTimelineWhere`, `opportunityTimelineEntryWhere`, the loaders on them, and the `assertRefs` keys `opportunityId` and `opportunityAttachmentId`, so the list, board, sidebar counts, get, patch, timeline, notes, attachments, email, email options, related, and anything linking to an opportunity leave deleted ones out. Every new opportunity query must go through one of those builders. Only these read deleted ones, on purpose: `viewableOpportunityIncludingDeletedWhere` (the opportunity's audit list, restore, undo, and `GET /api/opportunities/[id]` for `auditLog.view` holders, which then returns `deletedAt` and `deletedBy`), `deletedOpportunityWhere` (the restore write), `opportunityRecordStatesWhere` (the audit list's record states), the team, stage, and type in use counts (`DELETED_OPPORTUNITY` for the deleted part of the message), the stage category closedAt update, and `ensureTeamDefaults`.
- Undo (`POST /api/audit-log/[entryId]/undo`, `auditLog.restore`; another company's entry is a 404): only a `field_changed` entry of an opportunity field the PATCH takes, not undone yet, whose record isn't deleted, and with no later `field_changed` or `undone` entry for the same record and field. That rule is `undoBlockReason` in `src/lib/audit-values.ts`, used by both the route and every list's `canUndo` (`entryUndoBlockReason` / `loadUndoLookups` in `src/lib/audit-log.ts`). `undoOpportunityChange` (`src/lib/opportunity-undo.ts`) sends the before value through `planOpportunityUpdate` (every PATCH rule: the opportunity view check, the owner and team rules, contact and location belonging to the client, stage closedAt), and a refusal is a 409 with a plain reason (`undoRefusalMessage`, for example "This owner is no longer in the team"). Fields one change set together (`LINKED_UNDO_FIELDS`: client with contact and location, team with owner) are undone together when their entries in the same change can be undone too. One transaction claims each original (`undoneAt`, `undoneById`, a conditional write, so two undos never both apply), checks again that nothing changed since, applies the change with its timeline actions, and writes an `undone` entry (`undoOfId`) per field. Undo needs `auditLog.restore`, not `opportunities.edit`.
- Restore (`POST /api/opportunities/[id]/restore`, `auditLog.restore` plus the view check with deleted ones included): 409 `NOT_DELETED` when it isn't deleted; otherwise one transaction clears `deletedAt` and `deletedById` (only on a still deleted row) and writes a `restored` audit entry and a `restored` timeline action. # Sessions
- Sign in sessions are JWT cookies with their lifetimes in `src/lib/session-config.ts`: idle `SESSION_IDLE_SECONDS` (7 days, `session.maxAge`), refresh `SESSION_REFRESH_SECONDS` (1 day), and an absolute cap `SESSION_ABSOLUTE_SECONDS` (30 days from signing in).
- Auth.js only re-issues the cookie (moving its idle expiry forward) when `/api/auth/session` is fetched; `auth()` in pages and API routes never renews it. `SessionKeepAlive` (mounted by the dashboard layout) fetches it at most once per refresh period per browser, on load and hourly, so active users aren't signed out at 7 days.
- The jwt callback in `src/auth.ts` runs `sessionAfterCap`: sign in (password and SSO) stamps `signedInAt`; a token without it (issued before the cap) takes its `iat`, its last issue time, once; past the cap the callback returns null, so `auth()` returns null, the dashboard redirects to `/login`, API routes answer 401, and the cookie is cleared where Auth.js can set cookies. No database query is added. A deactivated user is still handled by the session callback (`session.user` becomes null).
- Deactivated and deleted users depend on next-auth's server side wrapper (`getSession` in `node_modules/next-auth/lib/index.js`), which builds the session as `{ user: user ?? token, ...session }`. That is why the session callback returns `user: null` instead of deleting `user`: a missing user would make `auth()` return the raw JWT as the user. Since 5.0.0-beta.32, `auth()` also returns null when Auth.js answers with an error (a broken configuration) instead of the error object. Every caller checks `session?.user` (or its `id`), never only that `auth()` returned something.
- `npm run check:auth` (`scripts/check-auth-session.ts`, no database or network) guards this. It runs the real `src/auth.ts` and the installed next-auth with only the database faked, calls the real `auth()` and `requireAccess()` inside a Next request scope, and checks that a deactivated or deleted user gets a session with `user: null` and a 401, that the wrapper still fills a missing user from the token, that a token past the absolute cap gets null and a cleared cookie, that a missing secret gets null, and that cookie names and attributes (`__Secure-` and `__Host-` on https, HttpOnly, SameSite=Lax), the credentials redirect, and the lockout code are unchanged. Exit 0 pass, 1 a check failed, 2 the harness broke.

# Rate limiting
- `src/lib/rate-limit.ts` limits public entry points by IP, counting failures only, in fixed windows stored in the `rate_limits` table (`RateLimit` model) with one `INSERT ... ON CONFLICT DO UPDATE` per failure. The IP is never stored: rows hold sha256 of `key:ip`. Rows older than two days are deleted by the limiter itself, at most every five minutes per instance.
- Keys and limits are `RATE_LIMITS`: `login` (wrong passwords and unknown emails, 20 per 15 minutes, checked with `isBlocked` before each attempt; a blocked IP gets the sign in code `ipblocked_N` and "Too many attempts from your network. Try again in N minutes." next to the unchanged per account lockout), `portal` (every link that doesn't open, 30 per 15 minutes, counted in `resolvePortalAccess`; a link that opens never touches the table, and an IP this instance already blocked is refused from memory), `sso-lookup` (every call, 30 per 15 minutes), and `csp-report` (every report, 300 per 15 minutes). A refusal is 429 with `Retry-After` and `{ error, code: "RATE_LIMITED", retryAfterSeconds }` (`rateLimitedResponse`).
- Fail open: any error (the table not migrated yet, a database error, a timeout over two seconds) lets the request through and logs at most one warning line per five minutes, without the IP. Success never writes.
- `getClientIp` reads the first `x-forwarded-for` entry (Vercel sets it), then `x-real-ip`. No usable IP, which includes loopback addresses in local development and the dev-only scripts, skips limiting entirely.
- Adding a key: add it to `RATE_LIMITS`, call `recordFailure(key, getClientIp(req))` on its failure path, and either check `isBlocked` before the attempt or answer `rateLimitedResponse` when `recordFailure` reports blocked.
- Per subject limits count every request instead of failures: `consume(key, subject, limit, windowMs)` (or `consumeSubject` with a `SUBJECT_LIMITS` rule) runs the same fixed window upsert with the subject (a customer link's token, or a user id) hashed with the key like an IP, one upsert per request, failing open with the same warning line. Today: `portal-pdf` and `portal-comment` (see the portal rules above), and `record-email` (the Email action, 30 per 10 minutes per user, `emailLimitedResponse`).

# Security headers
- `next.config.ts` `headers()` applies `securityHeaders` from `src/lib/security-headers.ts` to every route: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` plus an enforced `Content-Security-Policy: frame-ancestors 'none'` (nothing frames the app; PDFs download as attachments), `Permissions-Policy` turning off camera, microphone, geolocation, and payment, and `Reporting-Endpoints`. HSTS is left to Vercel. There is no proxy (middleware) file.
- `images.localPatterns` in `next.config.ts` limits the image optimizer (`/_next/image`) to `/icon.png`, the only file `next/image` shows (sidebar and Updates page); any other url gets a 400. Using `next/image` for another local file means adding its path there (in development a `src` that doesn't match throws). `remotePatterns` stays unset.
- The Content-Security-Policy (`buildCsp`, every source explained there) is sent as `Content-Security-Policy-Report-Only` while `CSP_MODE` is "report-only"; setting it to "enforce" sends the same policy as `Content-Security-Policy`. It is static, so it allows `'unsafe-inline'` scripts and styles; a new external origin (a CDN, an image host) goes into `buildCsp` first.
- `img-src` holds the uploads bucket's own origin (`uploadsImageOrigin`: `https://<bucket>.s3.<region>.amazonaws.com`) only when `AWS_S3_BUCKET_NAME` is a plain bucket name and `AWS_REGION` a plain region name at build time. Otherwise the bucket is left out (uploaded images don't load) and `headers()` logs one build time warning naming the variables (`uploadsImageOriginWarning`); it never falls back to a wildcard such as `https://*.amazonaws.com`, which would let any bucket serve images. `check:headers` fails on any wildcard host in `img-src`.
- Browsers post violations to `POST /api/csp-report` (public, `csp-report` rate limit), which reads at most 10 KB, logs one line `CSP violation: directive=... blocked=<origin> page=<path>` (portal tokens shown as `[token]`), stores nothing, never echoes the report, and answers 204.
- `npm run check:headers` (`scripts/check-headers.ts`, no database or secrets; `-- --base-url <url>`, default `http://localhost:3000`) fetches the login page, `/dashboard` (expects a redirect), `/api/users` (401), a portal page and API route, and posts a sample report (204), and checks every header. Exit 1 on any failure, 2 if the app can't be reached.

# Tickets
- Models (`prisma/schema.prisma`): `Ticket` (number unique per company, title, `clientId`, `contactId`, and `clientLocationId` all nullable, a contact and a location always of the client; `teamId` required, the queue, ON DELETE RESTRICT; `assigneeId` where null is unassigned; required `typeId`, `priorityId`, and `statusId`, ON DELETE RESTRICT; `source` MANUAL/EMAIL/NINJAONE, only MANUAL used so far; `statusChangedAt`, `resolvedAt`, `closedAt`; `deletedAt` and `deletedById` for the soft delete; `createdById` nullable, null for a ticket the system creates later), `TicketType`, `TicketPriority` (name, `sortOrder`), `TicketStatus` (name, `category` in `TicketStatusCategory`: OPEN, WAITING, RESOLVED, CLOSED, `sortOrder`), `TicketAttachment` (the same fields and scoping as `OpportunityAttachment`), and one `TicketSettings` row per company (`prefix`, default T; `defaultTeamId`, the queue a new ticket goes to, ON DELETE RESTRICT; `autoCloseResolvedDays`, default 7, 0 turns auto close off). `TimelineEntry.ticketId` (cascade), `ActionButton.fixedTicketStatusId` (RESTRICT), and `Team.roundRobinEnabled` / `Team.roundRobinLastUserId` (SET NULL) were added for them. No ticket screens exist yet; the ticket API is complete.
- Queues are teams: a ticket's `teamId` is its queue, and every Teams rule (members, default roles, the grant rules, the sidebar folder shape) applies. A team holding tickets (deleted ones included) can't be deleted (409 `TEAM_IN_USE`, `teamTicketsMessage`), and neither can the default ticket team (409 `DEFAULT_TICKET_TEAM`).
- Defaults are lazy: `ensureTicketDefaults(companyId)` (`src/lib/ticket-defaults.ts`) runs `ensureTeamDefaults` first (so General stays first in the order), then, when the company has no `TicketSettings` row, creates the types Incident, Service Request, Alert; the priorities Low, Medium, High, Urgent; the statuses New and Open (OPEN), Waiting on customer and On hold (WAITING), Resolved, and Closed; the settings (prefix T, 7 days); and the queues Helpdesk, Alerts, and Lv2 Escalation as teams after the existing ones, skipping any name a team already has (ignoring case), with Helpdesk (matched ignoring case) as `defaultTeamId`. Race safe like `ensureOpportunityDefaults`: the settings row insert (ON CONFLICT DO NOTHING) is the claim, and the queue teams are inserted with skip duplicates. Every ticket, ticket settings, and ticket attachment download route calls it first (the undo route for a ticket entry too); nothing else does. The default lists live in `src/lib/ticket-rules.ts`.
- Permission keys: `pages.tickets` (list and open tickets, read types, priorities, statuses, and settings), `tickets.create`, `tickets.edit` (fields, notes, attachments, the Email action), `tickets.delete`, `tickets.assign` (assign anyone in the ticket's team, and move tickets to any team), `tickets.viewTeam`, `tickets.viewAll`, and `settingsSections.tickets` (type, priority, status, and settings writes). Registered everywhere a key goes; Everyone has none, Global Admin all. The Roles screen shows them as "Tickets" (pages), "Ticket Actions", and "Ticket Settings".
- Visibility (`ticketVisibilityWhere` and the builders next to it in `src/lib/scoped-loaders.ts`: `ticketListWhere`, `ticketWhere`, `viewableTicketWhere`, `loadViewableTicket`, `ticketAttachmentWhere`, `ticketAttachmentsWhere`, `ticketTimelineWhere`, `ticketTimelineEntryWhere`, `loadTicketAttachment`, `loadTicketTimelineEntry`), the same three levels as opportunities through the shared `teamRecordVisibility` (the ticket's assignee in place of the owner), all needing `pages.tickets`: basic, tickets assigned to them plus unassigned ones in teams they belong to; `tickets.viewTeam`, theirs anywhere plus every ticket in their teams; `tickets.viewAll` (and Global Admin), every one. Anything else is a 404. `NOT_DELETED_TICKET` is built into every builder, so deleted tickets are never shown, to anyone (unlike opportunities, `GET /api/tickets/[id]` never opens a deleted one). Only the ticket's audit log, restore, and undo read deleted ones (`viewableTicketIncludingDeletedWhere`, `deletedTicketWhere`, `ticketRecordStatesWhere`). Every new ticket query goes through one of these builders.
- Assignment (`mayAssignTicketTo`): unassigned and the user themselves always; anyone with `tickets.assign`. The assignee must be an active user (400 "Invalid user") and a member of the ticket's team (400 "Assignee is not in this team", `ASSIGNEE_NOT_IN_TEAM`). Team rule (`mayUseTicketTeam`): a team the user belongs to, or any team with `tickets.assign` (a dispatcher escalating to another queue) or `tickets.viewAll`; on create the default ticket team is open to every creator. A team change whose assignee isn't in the new team needs a new assignee or `assigneeId: null` in the same PATCH. Refusals are 403 "You can only assign tickets to yourself or leave them unassigned" and "You can only move tickets to teams you belong to". The PATCH checks run through `planTeamPerson` (`src/lib/team-person-plan.ts`), shared with the opportunity owner rule.
- Round robin: with `Team.roundRobinEnabled` (`PATCH /api/teams/[id]` takes `roundRobinEnabled`, a boolean, with `settingsSections.teams`; `toTeamResponse` returns it), a ticket created unassigned in the team goes to the next active member after `roundRobinLastUserId`, in the shared user picker order (`compareUserNames`; `nextRoundRobinAssignee` in `src/lib/round-robin.ts`), skipping inactive members and starting after where a departed last member would sort. `takeRoundRobinAssignee` (`src/lib/ticket-create.ts`) locks the team row (`FOR UPDATE`) inside the create transaction and moves `roundRobinLastUserId`, so two creates take turns. The created entries describe the ticket unassigned; then an `assignee_changed` action (reason "Round robin") and a `field_changed` `assigneeId` audit entry are written by System. A named assignee is never changed and doesn't move the rotation.
- Statuses: a status's category is set when it is created and never changes (a PATCH naming another category is 400 `STATUS_CATEGORY_FIXED`; add a new status instead), so a category is never emptied by a change and no ticket's dates follow one. Every category keeps at least one status (delete 409 `LAST_STATUS_IN_CATEGORY`); a status in use (deleted tickets included) is 409 `STATUS_IN_USE`, and one an action button moves to is 409 `STATUS_USED_BY_BUTTON`. - Status dates (`statusTimestamps` / `ticketStatusChangeData` in `src/lib/ticket-rules.ts`, used on create, PATCH, notes, emails, and the auto close job): a move to another status sets `statusChangedAt`; into RESOLVED from another category sets `resolvedAt` (kept between two RESOLVED statuses) and clears `closedAt`; into CLOSED from another category sets `closedAt` (kept between two CLOSED statuses) and keeps `resolvedAt` (set now when it was never resolved); into OPEN or WAITING clears both. `moveTicketStatus` (`src/lib/ticket-update.ts`) applies a move inside a transaction.
- Numbers look like T-2026-0001: `takeRecordNumber(tx, companyId, "ticket", settings.prefix)` (the shared counter, Record numbers below), inside the create transaction. The prefix follows `numberPrefixProblem`, checked only when it changes.
- Creating goes through `createTicket` (`src/lib/ticket-create.ts`): one transaction that takes the number, creates the ticket, applies round robin, records `created` (timeline and audit), and writes the initial note a millisecond later (`writeInitialNote`). Its `initialNote` is `{ by: "person", userId, html }` or `{ by: "system", html }` (`InitialNote` in `src/lib/timeline.ts`, shared with opportunities). `POST /api/tickets` requires `title` and `initialNote` (400 "An initial note is required", judged after sanitizing) and takes `clientId`, `contactId` (400 "A contact needs a client" without one), `clientLocationId` (left out, the client's main location; null, none), `teamId` (left out, the default ticket team), `assigneeId` (left out, unassigned), and `typeId`, `priorityId`, `statusId` (left out, the first by `sortOrder`, the first OPEN status).
- Changes go through `planTicketUpdate` / `applyTicketUpdate` (`src/lib/ticket-update.ts`, shared by the PATCH and the undo): title, `clientId` (may be cleared; a client change without `contactId` clears the contact, and without `clientLocationId` resets the location to the new client's main location, none when cleared), `contactId` and `clientLocationId` (of the client), `teamId`, `assigneeId`, and `typeId`, `priorityId`, `statusId` (required, never cleared). Each changed field records one timeline action (`ticketChangeActions` in `src/lib/ticket-timeline.ts`: `status_changed`, `priority_changed`, `team_changed`, `assignee_changed`, `type_changed`, `client_changed`, `contact_changed`, `location_changed`, `title_changed`) and one `field_changed` audit entry (`ticketFieldAudits` in `src/lib/ticket-audit.ts`, through the shared `fieldChangedEntries` in `src/lib/audit-log.ts`); nothing for a PATCH that changes nothing.
- Routes (all `requireAccess`, company scoped, `ensureTicketDefaults` first): `GET/POST /api/tickets` (list filters `teamId`, `assigneeId` or `unassigned`, `statusId`, `statusCategory`, `priorityId`, `typeId`, `clientId`, `q` over title, number, and client name; query ids through `assertRefs`; newest first, unpaged like opportunities), `GET/PATCH/DELETE /api/tickets/[id]` (DELETE is a soft delete with `tickets.delete` and a `deleted` audit entry), `POST /api/tickets/[id]/restore` (`auditLog.restore`, `restoreDeletedRecord` in `src/lib/soft-delete.ts`, shared with opportunities), `GET/POST /api/tickets/[id]/timeline` (a note may carry `statusId` and `actionButtonId`; the move is stored on the note as `data.statusChange`, read with `noteStatusChange`, never as a separate entry), `PATCH/DELETE .../timeline/[entryId]` (own notes only, `noteChangeRefusal`), `GET/POST /api/tickets/[id]/attachments` and `DELETE .../attachments/[attachmentId]` (stored at `tickets/<id>/<uuid>.<ext>`, `ATTACHMENT` profile, returned with `withDownloadUrl("ticket", ...)`), `POST /api/tickets/[id]/email` and `GET .../email-options` (the shared `readEmailRequest` / `deliverRecordEmail` in `src/lib/record-email-delivery.ts`; EMAIL_OUT entry with `data.statusChange` for a move; contacts of the ticket's client, none without one), `GET /api/tickets/[id]/audit` (`auditLog.view` plus the view check, deleted ones included), `GET /api/tickets/sidebar-counts` (`sidebarCounts`, the opportunity folder's builder, counting OPEN and WAITING tickets by team and assignee), and `GET /api/files/ticket/[attachmentId]` (`pages.tickets` and the view check). # New records (opportunities and tickets)
- A new record starts Unassigned: no owner unless the person creating it picks one (the New opportunity dialog's Owner starts on Unassigned, and `POST /api/opportunities` with `ownerId` left out, null, or blank saves no owner). A named owner still follows the record's owner rule.
- A person creating a record must write an initial note, its first timeline entry. The dialog marks it required and won't save while its text is empty (judged on the text, not the markup, with `isBlankHtml`); `POST /api/opportunities` refuses a missing, non text, or empty `initialNote` with 400 "An initial note is required", judged after sanitizing, so a note that sanitizes to nothing (only a script tag, say) is empty.
- Creating an opportunity goes through `createOpportunity` (`src/lib/opportunity-create.ts`): one transaction that takes the number, creates it, records `created`, and saves the initial note a millisecond later. Its `initialNote` is `{ by: "person", userId, html }` (the route always passes this) or `{ by: "system", html }` for an automatic one (a later branch creates opportunities from a sent quote), written with no author so it reads as System; either is sanitized and refused when empty (a `UserError`). Tickets follow the same rules with their own function.

# List column filters
- HaloPSA style column filters for list tables (opportunities now, tickets later): `ColumnFilterToggle`, `ColumnFilterRow`, and `useColumnFilters` in `src/components/table/ColumnFilters.tsx`, rules in `src/lib/column-filters.ts`. A filter icon in the table's header row shows or hides a row of text boxes right under the column names, one per column, each as wide as its column and scrolling sideways with the table. A box filters its column with a case insensitive "contains" match against the text the column shows (each column gives `text(row)`, for example "Unassigned" for no owner, values and dates as displayed); several boxes combine with AND. The icon shows a dot while any box has text, and a "Clear filters" control with a "Showing N of M" count appears.
- Filters live in the URL as `f_<column key>=<text>` (for example `?view=list&f_client=acme&f_stage=won`), written once typing pauses, so a refresh or a shared link keeps them; the row opens by itself when the URL has one. Unknown keys are ignored and text is capped at `COLUMN_FILTER_MAX`.
- Matching runs on the rows already loaded for lists that aren't paged. A paged list (the audit log) uses server mode: it sends `applied` (the filters the URL holds, which follow the boxes once typing pauses) to its API and keeps the same `f_<column>` parameters, and a column with `filterable: false` gets an empty cell in the filter row.

# Design system conventions

# Windows environment note
- The `postinstall` script uses touch-style file creation for `.env`, which can behave unexpectedly on Windows. If a fresh `npm install` fails around `.env` creation, this is likely why, not a real project error.

# Deployment note
- After any merge into `main` that includes new Prisma migration files, `npx prisma migrate deploy` must be run against the live production database. This is a manual step performed by the project owner, not something to run automatically as part of a build or deploy script.
